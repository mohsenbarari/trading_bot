# Roadmap رصد موردی آفر در بات از روی لینک پست کانال

## وضعیت سند

- تاریخ ایجاد: `2026-07-16`
- برنچ: `candidate/bot-market-offer-monitoring`
- مبنا: `main@2d7c114d`
- وضعیت: `DRAFT_FOR_PRODUCT_REVIEW`
- این سند جایگزین برداشت اشتباه قبلی WebApp-first است.
- این سند مجوز کدنویسی feature، migration، staging deploy یا production deploy نیست.

## 1. اصلاح scope

نیاز محصول این نیست که در این مرحله پنل کامل رصد بازار WebApp ساخته شود.

نیاز فعلی این است که در بات تلگرام، داخل پنل مدیریتی، بخشی با عنوان `رصد بازار` اضافه شود. مدیر لینک پست آفر منتشر شده در کانال تلگرامی متصل به بات را paste می کند و بات اطلاعات موردی همان آفر را به صورت read-only برمی گرداند.

رصد بازار در WebApp همچنان نیاز واقعی پروژه است، اما نسخه WebApp کامل تر، گسترده تر و در roadmap/branch جداگانه طراحی و توسعه می شود. این برنچ فقط روی ابزار محدود و موردی داخل بات تمرکز دارد.

## 2. سناریوی کاربر

1. مدیر در بات وارد پنل مدیریتی می شود.
2. دکمه `رصد بازار` را می زند.
3. بات از مدیر می خواهد لینک پست آفر کانال را ارسال کند.
4. مدیر لینک پست آفر را paste می کند.
5. بات لینک را validate و parse می کند.
6. سیستم آفر متناظر را از دیتای داخلی پیدا می کند.
7. بات گزارش همان آفر را در private chat مدیر نمایش می دهد.

نمونه پیام شروع:

```text
لینک پست آفر منتشر شده در کانال را ارسال کنید.
```

نمونه خطای ورودی:

```text
آفری با این لینک پیدا نشد. لطفاً لینک پست آفر منتشر شده در کانال متصل به بات را ارسال کنید.
```

## 3. تعریف نسخه اول

نسخه اول `رصد بازار` در بات یک dashboard نیست. این بخش feed زنده، لیست همه آفرها، فیلترهای مدیریتی یا ابزار اقدام مدیریتی ندارد.

ورودی اصلی:

- لینک پست آفر منتشر شده در کانال تلگرام متصل به بات
- در صورت نیاز، متن شامل شناسه عمومی آفر

خروجی اصلی:

- خلاصه آفر
- ثبت کننده واقعی آفر
- سرور مرجع آفر
- وضعیت فعلی آفر
- وضعیت انتشار آفر در کانال تلگرام
- درخواست های ثبت شده روی همان آفر
- نتیجه درخواست ها و معامله نهایی، اگر وجود داشته باشد

## 4. داخل scope

- اضافه شدن دکمه `رصد بازار` فقط در پنل مدیریتی بات
- دسترسی فقط برای نقش های مدیریتی مجاز فعلی
- دریافت لینک پست آفر از مدیر
- استخراج شناسه قابل lookup از لینک:
  - `telegram_message_id`
  - یا `offer_public_id` اگر در متن ورودی وجود داشته باشد
- lookup آفر با مسیرهای امن:
  - `offer_public_id`
  - `channel_message_id`
  - `offer_publication_states.telegram_message_id`
- نمایش خلاصه آفر:
  - خرید/فروش
  - نقد حاضر/فردایی
  - کالا
  - مقدار اولیه
  - مقدار باقی مانده
  - قیمت
  - یکجا/خرد
  - lotها، اگر آفر خرد باشد
  - وضعیت active/completed/expired/cancelled
  - علت انقضا، اگر وجود داشته باشد
- نمایش ثبت کننده آفر:
  - نام کاربر در پروژه
  - نقش
  - وضعیت حساب
  - شناسه داخلی یا لینک پروفایل مدیریتی فقط اگر در سیاست فعلی admin مجاز باشد
- نمایش سرور مرجع:
  - `home_server`
  - وضعیت اینکه داده از sync محلی خوانده شده یا هنوز کامل نیست
- نمایش وضعیت انتشار:
  - message id کانال، اگر موجود است
  - وضعیت انتشار
  - خطای انتشار فقط با متن sanitize شده
- نمایش درخواست های ثبت شده روی آفر:
  - کاربر درخواست دهنده
  - actor، اگر متفاوت و مجاز به نمایش باشد
  - source surface: بات، WebApp یا مسیر داخلی
  - source server
  - زمان دریافت درخواست
  - زمان تصمیم
  - مقدار درخواست شده
  - lot انتخاب شده یا وضعیت lot، اگر قابل اتکا باشد
  - نتیجه درخواست
  - علت رد قابل نمایش، اگر وجود داشته باشد
  - trade id نهایی، اگر معامله انجام شده باشد
- نمایش اطلاعات معامله، اگر آفر معامله شده باشد:
  - خریدار
  - فروشنده
  - مقدار
  - قیمت موثر
  - زمان ثبت
  - سرور مرجع
- تست permission، لینک معتبر، لینک نامعتبر، آفرهای terminal و آفرهای دارای درخواست

## 5. خارج از scope

- ساخت پنل کامل رصد بازار در WebApp
- ساخت dashboard زنده در بات
- لیست تمام آفرها در بات
- فیلترهای مدیریتی گسترده در بات
- اقدام مدیریتی مستقیم مثل انقضا، هشدار، مسدودی یا محدودیت
- ارسال پیام جدید به کانال به دلیل باز شدن رصد
- تغییر رفتار بازار عمومی
- تغییر قوانین معامله، قیمت گذاری، تسویه، انقضا یا sync
- نمایش اطلاعات حساس بدون redaction
- production deploy بدون چرخه جداگانه

## 6. دلیل انتخاب مسیر bot-first برای این مرحله

این مسیر با نیاز فعلی مدیر سازگار است: مدیر معمولاً یک پست مشخص در کانال را می بیند و می خواهد بداند پشت آن آفر چه اتفاقی افتاده است.

مزیت های مسیر فعلی:

- کوچک و کم ریسک است.
- به UI کامل WebApp وابسته نیست.
- با محدودیت های تلگرام سازگار است، چون فقط یک گزارش موردی در private chat ارسال می شود.
- نیاز به feed، pagination و realtime جدید ندارد.
- رفتار عمومی بازار را تغییر نمی دهد.
- برای توسعه WebApp آینده یک read model قابل استفاده می سازد، بدون اینکه WebApp را در این مرحله وارد scope کند.

## 7. نقش ها و مجوز

نسخه اول فقط read-only است.

مجوز پیشنهادی:

| نقش | دسترسی |
| --- | --- |
| مدیر ارشد | مجاز |
| مدیر میانی | مجاز، اگر در سیاست فعلی پنل مدیریتی همین سطح دسترسی دارد |
| کاربر عادی | غیرمجاز |
| مشتری | غیرمجاز |
| حسابدار | غیرمجاز |
| کاربر بدون اتصال تلگرام معتبر | غیرمجاز |

اصل مهم:

مجوز باید در handler و service enforce شود. نمایش یا عدم نمایش دکمه به تنهایی کافی نیست.

## 8. پیدا کردن آفر از روی لینک پست

ورودی مدیر ممکن است یکی از این حالت ها باشد:

- لینک public channel post
- لینک private/supergroup channel post با فرمت داخلی Telegram
- متن کپی شده از پست که داخل آن `offer_public_id` وجود دارد
- فقط `offer_public_id`

قرارداد پیشنهادی:

1. ورودی normalize شود.
2. ابتدا `offer_public_id` از متن پیدا شود، اگر وجود دارد.
3. اگر نبود، `telegram_message_id` از لینک استخراج شود.
4. lookup فقط در مسیر admin-only انجام شود.
5. اگر چند نتیجه پیدا شد، سیستم بگوید ورودی مبهم است و حدس نزند.
6. اگر هیچ نتیجه ای پیدا نشد، پیام ساده و قابل فهم نمایش داده شود.
7. هیچ stack trace یا raw internal error در بات نمایش داده نشود.

## 9. چالش های فنی شناخته شده

### 9.1 انتخاب lot

در مدل فعلی ممکن است `offer_requests` فیلد صریح و پایدار برای `selected_lot_size` نداشته باشد.

مسیر کم ریسک:

- اگر lot انتخاب شده از trade یا داده پایدار قابل اتکا بود، نمایش داده شود.
- اگر قابل اتکا نبود، بات مقدار درخواست شده و وضعیت درخواست را نمایش دهد و کنار lot بنویسد `ثبت نشده` یا `قابل تشخیص نیست`.
- برای نسخه اول migration جدید فقط وقتی مجاز است که بدون آن گزارش غلط تولید شود.

### 9.2 sync بین ایران و خارج

بات روی سرور خارج اجرا می شود. بعضی آفرها یا درخواست ها ممکن است مرجعشان ایران باشد و داده از مسیر sync به سرور خارج رسیده باشد.

مسیر کم ریسک:

- گزارش از دیتای synced local خوانده شود.
- اگر آفر پیدا نشد یا داده ناقص بود، سیستم حدس نزند.
- پیام مناسب نمایش داده شود:

```text
اطلاعات این آفر هنوز کامل همگام سازی نشده یا با این لینک پیدا نشد.
```

در نسخه اول نباید برای این گزارش read-only مسیر sync یا authority پروژه بازطراحی شود.

### 9.3 طول پیام تلگرام

اگر آفر درخواست های زیادی داشته باشد، یک پیام تلگرام ممکن است طولانی شود.

مسیر کم ریسک:

- پیام اول خلاصه آفر و چند request آخر را نمایش دهد.
- اگر نیاز بود، گزارش در چند پیام کوتاه شکسته شود.
- هیچ pagination پیچیده ای در نسخه اول لازم نیست، مگر اینکه محدودیت طول پیام در تست واقعی فعال شود.

### 9.4 اطلاعات حساس

این گزارش برای مدیر است، اما باز هم نباید raw internal context، stack trace، secret، token یا اطلاعات غیرضروری نمایش داده شود.

مسیر کم ریسک:

- شماره موبایل فقط طبق سیاست فعلی نمایش اطلاعات مدیریتی نمایش داده شود.
- خطاهای داخلی sanitize شوند.
- نام تلگرام جای نام کاربر پروژه را نگیرد.

## 10. معماری پیشنهادی

برای جلوگیری از کپی کاری، منطق اصلی lookup و ساخت گزارش در یک service read-only قرار بگیرد.

پیشنهاد:

```text
core/admin_market_offer_monitoring.py
```

یا اگر ساختار فعلی پروژه مسیر service مشخص تری دارد، همان الگوی موجود رعایت شود.

مسئولیت service:

- parse ورودی
- lookup آفر
- جمع آوری publication state
- جمع آوری requestها
- جمع آوری tradeهای مرتبط
- ساخت DTO sanitize شده

مسئولیت handler بات:

- کنترل دسترسی
- دریافت لینک از مدیر
- فراخوانی service
- تبدیل DTO به پیام تلگرام
- مدیریت خطاهای قابل انتظار

نکته مهم:

این service بعداً می تواند پایه نسخه کامل WebApp باشد، اما در این برنچ WebApp UI ساخته نمی شود.

## 11. مراحل پیشنهادی

- تایید نهایی اینکه نسخه فعلی فقط داخل بات است.
- تایید نقش های مجاز.
- تایید میزان نمایش شماره تلفن و اطلاعات هویتی.
- تایید اینکه report فقط read-only است.

خروجی:

- همین roadmap به عنوان قرارداد scope.

### Stage 1 - parser و read model

هدف:

- ساخت parser لینک/متن ورودی.
- ساخت service read-only برای lookup آفر.
- خروجی DTO sanitize شده.

تست ها:

- لینک معتبر کانال
- لینک نامعتبر
- `offer_public_id`
- ورودی مبهم
- آفر پیدا نشده
- آفر با publication state
- آفر بدون publication state

### Stage 2 - flow بات در پنل مدیریتی

هدف:

- اضافه شدن دکمه `رصد بازار` در پنل مدیریتی بات.
- دریافت لینک از مدیر.
- نمایش گزارش آفر.
- برگشت امن به پنل مدیریت.

تست ها:

- مدیر مجاز
- کاربر غیرمجاز
- ارسال لینک صحیح
- ارسال متن اشتباه
- خروج از state
- عدم تداخل با broadcast، مشتریان، دعوت و سایر stateهای مدیریتی

### Stage 3 - جزئیات request و trade

هدف:

- نمایش درخواست های ثبت شده روی آفر.
- نمایش نتیجه درخواست ها.

تست ها:

سناریوها:

- آفر یکجا

### Stage 5 - مستندسازی handoff برای WebApp آینده

هدف:

- مشخص شود service ساخته شده چطور بعداً می تواند پایه پنل کامل WebApp باشد.

خروجی:

## 12. معیار پذیرش

این roadmap زمانی آماده ورود به توسعه است که موارد زیر روشن باشد:

- دکمه فقط در پنل مدیریتی بات اضافه می شود.
- WebApp کامل در این مرحله ساخته نمی شود.
- گزارش فقط برای یک آفر مشخص است.
- ورودی اصلی لینک پست کانال است.
- خروجی read-only است.
- اطلاعات حساس sanitize می شود.
- تغییر هیچ اثری روی ثبت، معامله، انقضا، انتشار یا sync آفر ندارد.
