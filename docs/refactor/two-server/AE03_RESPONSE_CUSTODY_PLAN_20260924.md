# AE03 response custody and no-replay plan (2026-09-24 UTC)

Status: **DESIGN / NOT ACTIVATED**. R1–R3 can read and validate a terminal quota receipt, but `serve`, the client and Supervisor do not call that reader. Supervisor is STOPPED. This plan does not authorize a live retry or a new semantic reservation.

## Current boundary and concrete failure windows

`_claim_next` moves a queue file from `requests/` to `claimed/` and immediately permits Provider execution; it does not fsync either queue directory after the move. `_recover_interrupted_claims` currently emits an ambiguous `BROKER_ERROR` for a claimed request and never checks a terminal receipt. `serve` publishes the response and then removes the claim, but does not publish a terminal quota receipt first. `_submit_request` removes the response file in `finally` **before** `validate_response`, and the orphan cleaner deletes old responses after 24 hours. These are source facts, not a claim that an incident has occurred.

| Failure moment | Current observable risk | Required safe result |
| --- | --- | --- |
| Crash after claim move but before Provider call | Rename durability not proven; startup might see request or claim. | No Provider call until the claim's destination and source directory state are durably fenced. Any duplicate/uncertain queue identity is blocked, not run. |
| Crash while Provider may have run, before a terminal receipt | A claimed request is ambiguous. | Keep same request/semantic identity blocked. Do not re-execute or manufacture a success receipt. |
| Valid quota result, crash after receipt but before queue response | Current recovery ignores the receipt. | Re-read exact receipt, match every request field and the existing detector witness, then reconstruct only the same response; never invoke Provider. |
| Response exists but client disconnects or validation fails | Current client removes the file before validation. | Preserve the terminal receipt as durable authority, and do not erase a response on invalid binding. Reattachment must use the same request ID and reservation, not a fresh submit. |
| STOP, restart or two wakeups during quota wait | Current runtime has no accepted wait contract. | STOP wins; one lock owner resumes once only after revalidating receipt, refs, task, assignment, controls and retry budget. |

## Implementation order and acceptance gates

1. **C1—durable claim admission.** Before calling Provider, validate the claimed file's exact ID/metadata and fsync both queue directories via the existing no-follow, inode-bound directory helper. A fsync error stops that call before Provider invocation. At startup, a request ID that appears in more than one queue/receipt location is not executed merely because it is in `requests/`. Tests inject failure at each fsync and a restart with duplicate IDs; an ambiguous case must fail closed. This is not a quota retry feature.
2. **C2—terminal custody before acknowledgement.** Only after the existing strict detector positively identifies a quota result, publish and fsync its immutable receipt **before** the response queue file or claim deletion. A receipt publication/verification failure must not be converted into an ordinary retryable result. Non-quota responses retain current behavior. Tests stop at every publication boundary and assert no Provider replay; reject receipt collision/mismatch.
3. **C3—restart recovery.** For a claimed request, a valid receipt whose full request equals the claimed document may reconstruct its exact original response without Provider. A missing receipt yields the existing ambiguous error; a corrupt, linked, mismatched or conflicting receipt/response causes hard stop, not fallback execution. Recovery must be idempotent across a second restart. Any orphan `requests/` entry sharing an ID with a claim, response or receipt is fenced.
4. **C4—client custody and same-identity reattachment.** Validate a response before deletion; keep terminal authority until a durable Supervisor decision is recorded. A disconnected client may reattach only to its persisted exact request ID/semantic reservation. No fresh `make_request` or task alias is a recovery path. Bound retention explicitly; never prune a receipt that a live wait/recovery state still references.
5. **C5—restart-safe quota wait.** Add typed `WAITING_QUOTA` state under the existing Supervisor lock, with known UTC reset or bounded `UNKNOWN` next-check. STOP, stale refs, changed assignment/control, invalid witness, quota budget and ambiguous effects prevent wakeup. Monitor observes but cannot grant authority. Fake-clock, clock-jump, two-wakeup and restart tests precede any live Supervisor activation.
6. **C6—full fault matrix and measured pilot.** Run deterministic crash/fault tests at every `rename/fsync/receipt/response/ack/prune` boundary, then 1/3/10/20 comparable live cohorts. Count failed/corrected attempts, Gemini and Codex usage, elapsed and active time. Only after quality and safety hold may AE03 be called complete; improvement remains UNKNOWN until measured.

Each C unit is separately scoped to one small change, Gemini Worker → independent Gemini Reviewer → Codex exact binding, semantic review, tests and Git. A green unit is not permission to skip later gates. Do not touch `main`, production, DNS, Web Writer or run a live quota replay during preparation.
