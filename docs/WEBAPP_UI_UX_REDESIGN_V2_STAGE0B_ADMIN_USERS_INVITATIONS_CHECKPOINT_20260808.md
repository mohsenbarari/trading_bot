# Stage 0B-4 — مدیریت کاربران و دعوت‌های استاندارد

تاریخ: ۲۰۲۶-۰۸-۰۸

وضعیت: **تکمیل و با تأیید صریح بصری مالک محصول در ۲۰۲۶-۰۸-۰۸ بسته شده است**؛ Phase 0، Figma، evidence محلی و Sites خصوصی ثبت شده‌اند؛ design-only و بدون مجوز تغییر کد محصول

شاخه: `condidate/webapp-ui-ux-redesign-v2`

جهت مصوب: **مالی مدرن، خلوت و mobile-first**

## ۱. تصمیم و دامنه checkpoint

مالک محصول خروجی `0B-3` و قرارداد Phase 0 این checkpoint را تأیید کرد. این checkpoint تجربه مدیریت کاربر و دعوت استاندارد را برای مدیر میانی و مدیر ارشد تعریف می‌کند، بدون آنکه قابلیت تازه‌ای را به API یا بات نسبت دهد.

سطح‌های داخل دامنه:

- ورودی مدیریت برای مدیر میانی؛
- جست‌وجو و فهرست کاربران؛
- جزئیات کاربر و اقدام‌های مجاز؛
- محدودیت معامله؛
- محدودیت‌های تعدادی؛
- غیرفعال‌سازی حساب؛
- کنترل‌های پیشرفته و ارجاع به قرارداد حذف حساب؛
- ساخت دعوت استاندارد، نتیجه دعوت و صف دعوت‌های در انتظار؛
- state، recovery، permission و responsive/desktop proof.

سطح‌های خارج از دامنه:

- UI و رفتار داخلی بازار و پیام‌رسان؛
- کالاها، کانال‌ها، پیام‌های مدیریت و تنظیمات سیستم؛
- دعوت رابطه مشتری/حسابدار؛
- هشدار مستقل مدیریتی، چون چنین قابلیت مستقلی در Web، Bot یا API فعلی وجود ندارد؛
- resend، history و bulk action برای دعوت‌ها؛
- هر تغییر runtime، API، permission، دیتابیس یا رفتار بات.

شروع پیاده‌سازی همچنان تا تأیید صریح `0B-6` ممنوع است.

## ۲. هدف سناریویی

ادمین باید بتواند:

1. از ورودی مدیریت فقط مقصدهای واقعی و مجاز را ببیند؛
2. کاربر را با جست‌وجوی پایدار پیدا کند؛
3. هویت، وضعیت و محدودیت مؤثر بر تصمیم را بدون metadata بی‌اثر بررسی کند؛
4. نوع اقدام را درست تشخیص دهد و پیامد آن را پیش از ثبت بفهمد؛
5. نتیجه موفق یا ناموفق را در همان context ببیند؛
6. دعوت استاندارد را بسازد، کانال‌های واقعاً در دسترس را دریافت کند یا دعوت در انتظار را لغو کند؛
7. در حالت فاقد permission، هدف شخصی یا هدف هم‌سطح، با UI محافظت‌شده روبه‌رو شود.

فضای بیشتر دسکتاپ فقط برای master/detail همان کار استفاده می‌شود و مجوز افزودن KPI، نمودار، تعداد ابزار یا واقعیت تازه نیست.

## ۴. قرارداد ورودی مدیریت و فهرست کاربران

- ورودی مدیر میانی فقط مقصدهای «کاربران» و «دعوت‌ها» را نشان می‌دهد.
- تعداد دسته‌ها، ابزارها، نقش جاری و جمله‌ای مانند «بر اساس دسترسی شما» محتوای کاربر نیستند.
- endpoint دعوت‌های pending حداکثر ۱۰۰ مورد و بدون total معتبر برمی‌گرداند؛ بنابراین `array.length` هرگز به‌عنوان تعداد کل نمایش داده نمی‌شود.
- فقط نشان غیرعددی «نیازمند رسیدگی» هنگام وجود مورد pending بارگذاری‌شده مجاز است و باید ورود مستقیم به همان صف را فراهم کند.
- صف می‌تواند موارد بارگذاری‌شده را بدون ادعای total نمایش دهد. count authoritative و pagination واقعی carry-forward صریح پیاده‌سازی‌اند.
- جست‌وجو هنگام ورود به جزئیات و بازگشت حفظ می‌شود.
- فیلتر نقش یا وضعیت طراحی نمی‌شود، چون API فعلی آن را پشتیبانی نمی‌کند و فیلترکردن client-side روی بخشی از نتایج، تصویر گمراه‌کننده می‌سازد.
- هر ردیف فقط هویت لازم، نقش/سطح و سرگروه لازم برای تصمیم، وضعیت مؤثر و affordance ورود را نگه می‌دارد.
- تعداد کل کاربران، آمار نقش‌ها، مسیر داخلی، شناسه سرور و metadata پشتیبانی در نمای پیش‌فرض جایی ندارند.

## ۵. قرارداد اقدام‌های مدیریتی

چهار مفهوم زیر در UI و copy با هم ادغام نمی‌شوند:

1. **محدودیت معامله:** جلوگیری از ساخت آفر یا معامله، با حفظ ورود کاربر؛
2. **محدودیت‌های تعدادی:** سه سهمیه کمی با reset شمارنده‌ها و مهلت پایان محدود؛
3. **غیرفعال‌سازی حساب:** copy دقیق confirm برابر است با «فوری: بازار بسته می‌شود. خروج کاربر از کانال تلگرام مورد انتظار است؛ نتیجه آن در این صفحه قابل‌تأیید نیست.»؛ سپس قفل سراسری Web/Messenger و لغو نشست‌ها پس از مهلت دو روزه توضیح داده می‌شود؛
4. **حذف حساب:** اقدام cascade‌شونده و پرریسک مطابق قرارداد canonical `0B3-M10`.

داده canonical prototype برای کنترل drift:

- `M04`: status دقیق `وضعیت: فعال ← محدود` و دقیقاً یک تاریخ در ردیف مستقل `پایان: ۲۲ مرداد ۱۴۰۵، ساعت ۱۴:۳۰`؛
- `M05`: معامله روزانه `۲۰ ← ۱۰`، **تعداد کالای معامله‌شده** `۵۰۰ ← ۳۰۰` و درخواست آفر کانال `۶ ← ۴`، با همان پایان `۲۲ مرداد ۱۴۰۵، ۱۴:۳۰`؛ واحد سهمیه دوم «عدد کالا» است و هر اشاره به گرم ممنوع است؛
- `M06`: deadline فعال‌سازی مجدد `۱۹ مرداد ۱۴۰۵، ۱۴:۳۰`.

غیرفعال‌سازی حساب **آفرهای فعال را expire/collect نمی‌کند**. انقضا/جمع‌آوری آفر و cascadeهای وابسته فقط متعلق به حذف حساب‌اند و نباید در copy، confirm یا success غیرفعال‌سازی ادغام شوند.

برای هر اقدام:

- مقدار یا وضعیت فعلی و پیشنهاد جدید پیش از ثبت قابل مقایسه است؛
- اثر و deadline واقعی در نقطه تصمیم دیده می‌شود؛
- CTA نام دقیق همان عمل را دارد؛
- busy، success و failure در همان context باقی می‌مانند؛
- شکست درخواست، انتخاب و داده واردشده را بی‌دلیل پاک نمی‌کند.

در نتیجه موفق غیرفعال‌سازی فقط این موارد ادعا می‌شوند:

- وضعیت قابل مشاهده حساب و deadline `۱۹ مرداد ۱۴۰۵، ۱۴:۳۰` به‌روزرسانی شده است؛

confirm فقط outcome موردانتظار خروج از کانال را با copy canonical بالا توضیح می‌دهد. success صرفاً وضعیت حساب و deadline را نمایش می‌دهد و هیچ وضعیت اجرایی یا نتیجه‌ای برای side-effect کانال/Telegram ادعا نمی‌کند؛ receipt مستقل و معتبر یک carry-forward اجرایی است.

گزینه «محدودیت تعدادی دائمی» در prototype وجود ندارد. رفتار فعلی Web و Bot برای این حالت هم‌معنا نیست و ممکن است در Web عملاً محدودیتی ایجاد نکند؛ تا رفع قرارداد cross-platform، فقط پایان محدود و صریح طراحی می‌شود.

## ۶. قرارداد هشدار و حقیقت بین پلتفرم‌ها

- اقدام مستقل «ارسال هشدار» در این checkpoint وجود ندارد، زیرا Web، Bot و API فعلی چنین قابلیت مستقلی ندارند.
- اعلان یا متنی با عنوان «اخطار» که به‌عنوان پیامد بعضی محدودیت‌ها ساخته می‌شود، جای قابلیت مستقل هشدار را نمی‌گیرد.
- نیاز هشدار مستقل در roadmap جداگانه رصد بازار دنبال می‌شود و این Stage UI خیالی برای آن نمی‌سازد.
- design نباید موفقیت تحویل Telegram را ادعا کند، چون پاسخ mutation فعلی چنین رسیدی ارائه نمی‌کند.
- write مدیریتی Bot ممکن است خارج از سرور authority ایران رد شود؛ prototype صرفاً قرارداد تجربه است و parity اجرایی را اثبات نمی‌کند.

## ۷. قرارداد مجوز و اهداف محافظت‌شده

| وضعیت | قرارداد نمایش و اقدام |
| --- | --- |
| مدیر میانی | هیچ **ادمین دیگری** را به‌عنوان target دریافت نمی‌کند؛ حساب خودش استثنای قابل مشاهده اما read-only و محافظت‌شده است؛ فقط کاربران غیرادمین را مدیریت می‌کند |
| مدیر ارشد | کاربران سطوح پایین‌تر را مدیریت می‌کند؛ ساخت دعوت مدیر ارشد مجاز نیست |
| هدف شخصی برای هر ادمین | قابل مشاهده اما کاملاً read-only: تغییر نقش، محدودیت معامله، محدودیت تعدادی، غیرفعال‌سازی، پایان نشست‌ها و حذف همگی ممنوع‌اند |
| مدیر ارشد هم‌سطح دیگر | قابل مشاهده اما برای تمام اقدام‌های حساس، از جمله تغییر نقش، محدودیت معامله، محدودیت تعدادی، غیرفعال‌سازی، پایان نشست‌ها و حذف، read-only است |
| permission نامعتبر یا تغییرکرده | صفحه به empty یا success دروغین تبدیل نمی‌شود؛ توضیح کوتاه و بازگشت معتبر ارائه می‌شود |

این جدول **قرارداد طراحی Stage 0B-4 و carry-forward الزام‌آور backend** است، نه توصیف رفتار فعلی backend. backend فعلی همه این guardها را enforce نمی‌کند. تکمیل enforcement نباید صرفاً به disabledبودن دکمه در frontend واگذار شود.

| --- | --- | --- | --- | --- | --- | --- | --- |
| مدیر میانی / کاربر غیرادمین | مجاز | read-only | مجاز | مجاز | مجاز | مجاز | مجاز |
| مدیر میانی / خودش | مجاز | read-only | read-only | read-only | read-only | read-only | read-only |
| مدیر میانی / هر مدیر دیگر | هدف اصلاً دریافت نمی‌شود | — | — | — | — | — | — |
| مدیر ارشد / نقش پایین‌تر | مجاز | مجاز | مجاز | مجاز | مجاز | مجاز | مجاز |
| مدیر ارشد / خودش | مجاز | read-only | read-only | read-only | read-only | read-only | read-only |

Backend فعلی می‌تواند دعوت مدیر ارشد را بپذیرد، با اینکه clientهای مصوب آن را ارائه نمی‌کنند. API باید در پیاده‌سازی آینده همان منع را enforce کند.

## ۸. قرارداد دعوت استاندارد

- فرم فقط نقش‌های مجاز ادمین جاری را نشان می‌دهد: مدیر میانی دقیقاً `watch` و `standard`؛ مدیر ارشد دقیقاً `watch`، `standard`، `police` و `middle`؛ نقش `super` هرگز ارائه نمی‌شود.
- نتیجه باید روشن کند دعوت **تازه ساخته شده** یا یک دعوت **هنوز فعال بازیابی شده** است.
- فقط لینک Web یا Telegram که واقعاً موجود است نمایش و برای copy ارائه می‌شود.
- URL خام در هیچ product surface، حتی fallback شکست clipboard، نمایش داده نمی‌شود؛ recovery شامل retry copy یا بازکردن مستقیم همان مقصد موجود است.
- مهلت دعوت و وضعیت واقعی SMS نمایش داده می‌شوند؛ محصول تحویل Telegram را بدون receipt ادعا نمی‌کند.
- ارسال SMS فعلی یک‌بار انجام می‌شود؛ resend، history و bulk action در این Stage ساخته نمی‌شوند.
- مدیر میانی فقط دعوت‌های pending ساخته‌شده توسط خودش را می‌بیند و revoke می‌کند؛ مدیر ارشد همه دعوت‌های pending را می‌بیند و revoke می‌کند.
- revoke فقط برای دعوتی که هنوز pending است ارائه می‌شود و پس از تغییر وضعیت، recovery روشن دارد.

## ۹. قرارداد state و recovery

state atlas این حالت‌ها را جدا می‌کند:

| state | آنچه باید دیده شود | آنچه نباید دیده شود |
| --- | --- | --- |
| Loading | skeleton هم‌شکل فهرست/جزئیات بدون داده فرضی | نام، نقش، تعداد، permission یا وضعیت ساختگی |
| Load error | پیام cause-neutral و retry نزدیک | empty دروغین، صفحه سفید یا blame قطعی شبکه |
| True empty | توضیح کوتاه و اقدام مجاز | KPI صفر، کارت تزئینی یا دعوت ناممکن |
| Search empty | query حفظ‌شده و پاک‌کردن جست‌وجو | پیام «هنوز کاربری نیست» |
| Missing/deleted detail | توضیح حذف/عدم دسترسی و بازگشت معتبر | spinner نامحدود یا شناسه فنی |
| Permission/self protected | علت کوتاهِ اثرگذار و action امن | کنترل مخرب فعال یا افشای سیاست داخلی |
| Busy/success/failure | feedback کنار همان action | toast مبهم یا reset زودهنگام context |
| Clipboard failure | retry copy یا بازکردن مستقیم مقصد موجود | ادعای copy موفق یا نمایش URL خام |
| Invitation no longer pending | وضعیت تازه و راه بازگشت/refresh | revoke موفق دروغین |

## ۱۰. قرارداد adaptive desktop

- پنج proof موبایل برای عرض‌های `360 / 375 / 390 / 414 / 430` از فهرست کاربران ساخته می‌شود.
- proof دسکتاپ دقیقاً `1440×900` و به‌شکل user directory master/detail است.
- موبایل در هر لحظه فهرست یا جزئیات را نشان می‌دهد؛ دسکتاپ می‌تواند همان دو بخش را هم‌زمان نمایش دهد.
- query، انتخاب و context فهرست در جابه‌جایی حفظ می‌شوند.
- دسکتاپ هیچ KPI، نمودار، sidebar تازه یا metadataای که در موبایل لازم نبود اضافه نمی‌کند.

### invariant پوسته از Stage 0B-2

پوسته احراز‌شده این Stage قرارداد تأییدشده `0B-2` را بدون تفسیر تازه reuse می‌کند:

- ترتیب و label دقیق navigation: `خانه`، `بازار`، `پیام‌رسان`، `عملیات`، `حساب`؛
- مقصد فعال در سطح‌های مدیریتی این checkpoint: `عملیات`؛
- iconها با همان treatment مصوب SVG، بدون emoji، glyph جایگزین یا خانواده icon تازه؛

## ۱۳. حدود ادعا و carry-forward پیاده‌سازی

Figma، Sites و evidence ایستا نمی‌توانند authorization واقعی، forwarding میان سرورها، mutation authority، reset سهمیه، deadline، لغو نشست، تحویل SMS/Telegram، clipboard، router history، focus management، screen reader، keyboard موبایل یا شکست شبکه را اثبات کنند.

موارد الزام‌آور برای پیاده‌سازی آینده:

- API جست‌وجو/فیلتر کامل یا حذف صادقانه filterهای ناقص؛
- count authoritative و pagination واقعی برای صف pending؛ تا آن زمان هیچ total عددی ساخته نشود؛
- enforcement سمت سرور برای self-target، same-level و دعوت مدیر ارشد؛
- قرارداد یکسان و محدود برای deadline محدودیت‌های تعدادی در Web و Bot؛
- forwarding یا failure contract روشن برای writeهای Bot خارج از authority؛
- جداسازی semantic چهار اقدام مدیریتی در API، copy و UI؛
- ادعای delivery فقط با receipt واقعی؛
- حفظ query/context و feedback همان‌جا؛
- visual freeze بازار و پیام‌رسان در هر تغییر component/token مشترک.
