# Stage 0B-3 — عملیات و workspace مشتری/حسابدار

تاریخ: ۲۰۲۶-۰۸-۰۸

وضعیت: طراحی و شواهد فنی تکمیل شده و در انتظار تأیید صریح مالک محصول است؛ design-only و بدون مجوز تغییر کد محصول

شاخه: `condidate/webapp-ui-ux-redesign-v2`

جهت مصوب: **مالی مدرن، خلوت و mobile-first**

## ۱. تصمیم و دامنه checkpoint

مالک محصول عبور از `0B-2` و ادامه مسیر با Figma رسمی را مجاز کرد. تأیید دستیاران خارجی فعلاً گیت پیشروی نیست، اما یافته‌های معتبر پیشین و پروتکل بازبینی برای استفاده احتمالی آینده حفظ می‌شوند.

این checkpoint قرارداد تجربه و شواهد طراحی این سطح‌ها را می‌بندد:

- مقصد نقش‌محور «عملیات»؛
- فهرست و جزئیات مشتریان؛
- فهرست و جزئیات حسابداران؛
- ویرایش مالی مشتری و شرح وظیفه حسابدار؛
- دعوت در انتظار و اقدام‌های copy/cancel؛
- پایان نشست و حذف حساب به‌عنوان اقدام‌های حساس؛
- loading، error، empty، نتیجه جست‌وجوی خالی و deep link نامعتبر؛
- تطبیق پنج عرض موبایل و یک proof واقعی master/detail دسکتاپ.

هیچ فایل runtime، API، permission، منطق کسب‌وکار یا UI داخلی بازار و پیام‌رسان در این Stage تغییر نکرده است. شروع پیاده‌سازی همچنان تا تأیید صریح `0B-6` ممنوع است.

## ۲. هدف سناریویی

مالک یا سرگروه باید بتواند:

1. از «عملیات» فقط مقصدهای واقعاً مجاز را ببیند؛
2. رابطه موردنظر را با جست‌وجو پیدا کند؛
3. روی موبایل وارد یک جزئیات مستقل شود و با Back به همان query، فیلتر و موقعیت scroll برگردد؛
4. تغییر را پیش از ثبت مرور کند و اثر آن را بفهمد؛
5. نتیجه موفق یا ناموفق را در همان context ببیند؛
6. پیش از اقدام حساس، پیامد کامل و واقعی آن را بداند.

فضای بیشتر دسکتاپ فقط برای هم‌زمان‌کردن list/detail لازم استفاده می‌شود و مجوز افزودن آمار، metadata یا واقعیت تازه نیست.

## ۴. قرارداد «عملیات» نقش‌محور

- مقصدی که کاربر مجوز یا کار واقعی برای آن ندارد اصلاً نمایش داده نمی‌شود.
- حسابدار destinationهای مالک برای مشتری/حسابدار را نمی‌بیند؛ وجود route در frontend مجوز ساخت dead action نیست.
- نقش، تعداد مسیر، تعداد ابزار و جمله‌هایی مانند «بر اساس دسترسی شما» محتوای کاربر نیستند.
- اگر هیچ اقدام عملیاتی وجود ندارد، empty کوتاه همراه با یک مقصد واقعی جای کارت‌های غیرفعال را می‌گیرد.
- بازار و پیام‌رسان فقط به‌عنوان مقصدهای shell موجود دیده می‌شوند؛ interior آن‌ها نه بررسی شده و نه بازطراحی.

## ۵. قرارداد workspace روی موبایل

- موبایل در هر لحظه **فهرست یا جزئیات** را نشان می‌دهد، نه هر دو را.
- ورود به جزئیات query، فیلتر مؤثر و scroll فهرست را حفظ می‌کند.
- Back از جزئیات به همان context فهرست بازمی‌گردد؛ deep link نامعتبر به صفحه خالی ختم نمی‌شود.
- ردیف رابطه فقط هویت، یک disambiguator لازم، وضعیت اثرگذار بر اقدام و affordance ورود را نگه می‌دارد.
- تعداد کل روابط badge نمی‌شود. شمارنده فقط برای صف واقعاً نیازمند اقدام، مانند دعوت در انتظار، مجاز است.
- اقدام‌های پرتکرار نزدیک محتوای اصلی‌اند؛ action خطرناک از اقدام عادی جدا و با فاصله و لحن مناسب نمایش داده می‌شود.
- feedback copy، cancel، save یا terminate در همان context مبدأ باقی می‌ماند.

## ۶. قرارداد تغییرات مالی

ویرایش سطح، نرخ/کارمزد یا حدود مشتری یک عملیات ساده «ذخیره» نیست. پیش از ثبت:

- مقدار قبلی و مقدار پیشنهادی قابل مقایسه است؛
- اثر تغییر صریحاً «برای فعالیت‌های بعدی» بیان می‌شود؛
- مشخص است که سوابق و محاسبات تکمیل‌شده تغییر نمی‌کنند؛
- ثبت نهایی پس از مرور انجام می‌شود؛
- شکست درخواست، داده واردشده و context کاربر را از بین نمی‌برد.

این checkpoint قرارداد ارائه را تعیین می‌کند و هیچ عدد، قاعده مالی یا اختیار backend تازه‌ای نمی‌سازد.

## ۷. قرارداد اقدام‌های حساس و حقیقت محصول

### پایان نشست

- فقط دستگاه/پلتفرم، آخرین فعالیت و در صورت لزوم اصلی یا جاری‌بودن نشست دیده می‌شود.
- `home_server`، نام سرور، مسیر API، منبع backend و metadata زیرساختی نمایش داده نمی‌شوند.
- confirm می‌گوید کاربر فوراً از همان دستگاه خارج می‌شود.
- busy، failure و success باید کنار همان اقدام باقی بمانند.

### حذف حساب و قطع ارتباط

عمل فعلی «unlink» یک قطع رابطه سبک نیست و حذف حساب cascade‌شونده انجام می‌دهد. بنابراین confirm باید پیش از اجرا روشن کند که:

- دسترسی وب‌اپ و بات غیرفعال می‌شود؛
- همه نشست‌ها پایان می‌یابد؛
- آفرهای فعال منقضی می‌شوند؛
- دعوت‌های در انتظار لغو می‌شوند؛
- همه روابط مشتری/حسابدارِ متعلق یا لینک‌شده، همراه با وابستگی‌های آن‌ها، به‌صورت بازگشتی بسته یا حذف می‌شوند.

نام شخص در نقطه تأیید نمایش داده می‌شود و CTA از واژه دقیق «حذف حساب» استفاده می‌کند. خلوت‌سازی مجوز پنهان‌کردن پیامد امنیتی یا تجاری نیست.

## ۸. قرارداد state و recovery

| state | آنچه باید دیده شود | آنچه نباید دیده شود |
| --- | --- | --- |
| Loading | skeleton هم‌شکل فهرست یا جزئیات | نام، تعداد، وضعیت یا permission فرضی |
| Load error | پیام cause-neutral و retry نزدیک | empty دروغین، صفحه سفید یا مقصر دانستن قطعی اینترنت |
| True empty | توضیح کوتاه و افزودن در صورت مجازبودن | آمار صفر، کارت تزئینی یا CTA ناممکن |
| Search empty | query حفظ‌شده و «پاک‌کردن جست‌وجو» | پیام «هنوز رابطه‌ای ندارید» |
| Missing detail | توضیح حذف/عدم دسترسی و بازگشت به فهرست | spinner بی‌نهایت یا route/path فنی |

## ۹. قرارداد adaptive desktop

- proof دسکتاپ دقیقاً `1440×900` است.
- فهرست و جزئیات مشتری هم‌زمان در master/detail دیده می‌شوند.
- انتخاب ردیف، context فهرست را نگه می‌دارد و جزئیات را عوض می‌کند.
- همان hierarchy، copy و اقتصاد اطلاعات موبایل حفظ می‌شود.
- فضای خالی با KPI، کارت summary، sidebar تازه یا metadata اضافی پر نمی‌شود.
- navigation architecture تازه‌ای برای محصول ساخته نمی‌شود.

## ۱۲. معیار پذیرش

- آزمون پنج‌ثانیه‌ای، مقصد عملیات یا task جاری را روشن کند.
- حسابدار هیچ destination مرده مخصوص مالک نبیند.
- موبایل list و detail را هم‌زمان نشان ندهد و Back context را بازیابی کند.
- ردیف‌ها شمارنده کل رابطه، metadata فنی یا اطلاعات تکراری نداشته باشند.
- صف دعوت در انتظار فقط چون اقدام‌پذیر است می‌تواند count داشته باشد.
- مرور تغییر مالی before/after و اثر future-only را روشن کند.
- اقدام حساس busy، confirm، پیامد صادقانه و feedback همان‌جا داشته باشد.
- حذف حساب با تمام cascade واقعی توضیح داده شود و با unlink کم‌خطر نمایش داده نشود.
- `home_server`، route، API، backend و server در قاب محصول وجود نداشته باشد.
- loading، error، true empty، search empty و missing detail با هم اشتباه نشوند.
- پنج عرض موبایل `360 / 375 / 390 / 414 / 430` بدون overflow باشند.
- proof دسکتاپ ۱۴۴۰×۹۰۰ master/detail واقعی باشد و اطلاعات تازه‌ای فقط برای پرکردن فضا نسازد.
- target عمومی حداقل ۴۴×۴۴ و CTA حداقل ۴۸ پیکسل ارتفاع داشته باشد؛ ممیزی Figma targetهای معنایی این Stage را حداقل `48×44` ثبت کرده است.
- کنتراست متن عادی حداقل ۴٫۵:۱ و focus/state غیرمتنی حداقل ۳:۱ باشد.
- هیچ UI یا رفتار داخلی بازار و پیام‌رسان تغییر نکند.
- هیچ کد runtime تا تأیید صریح `0B-6` تغییر نکند.

## ۱۳. حدود ادعا و carry-forward پیاده‌سازی

Figma و evidence ایستا نمی‌توانند API واقعی، permission backend، حفظ واقعی scroll/query در router، focus management، screen reader، busy state، شکست شبکه، کیبورد موبایل یا cascade اجرایی حذف را اثبات کنند. این موارد در Stageهای اجرایی ۱، ۴، ۵، ۷ و ۸ آزمون می‌شوند.

موارد الزام‌آور برای پیاده‌سازی آینده:

- UI نباید destinationهایی را نشان دهد که API برای نقش حسابدار رد می‌کند؛
- state فهرست باید پیش از ورود به جزئیات snapshot و در Back بازیابی شود؛
- نتیجه action در component یا context مبدأ باقی بماند؛
- ویرایش مالی review مرحله‌ای و future-only داشته باشد؛
- حذف حساب با semantics و cascade واقعی backend هم‌نام شود؛
- اطلاعات زیرساختی نشست، از جمله `home_server`، از UI محصول حذف شود؛
- هر تغییر component/token مشترک با visual freeze بازار و پیام‌رسان کنترل شود.
