## AMM-C01 - قرارداد دقیق feed بدون فیلتر

### وضعیت

`DECIDED`

### پرسش

عبارت «همان آفرهای بازار» در صفحه `رصد بازار` دقیقاً به چه مجموعه‌ای از آفرهای active و terminal، با چه ترتیب، pagination و رفتار Realtime اشاره می‌کند؟

### واقعیت فعلی بازار

در baseline فعلی، صفحه عمومی بازار یک feed مرکب می‌سازد:

- فیلتر پیش‌فرض نوع آفر `همه` است.
- فیلتر پیش‌فرض نوع تسویه `همه تسویه‌ها` است.
- آفرهای active از `GET /api/offers/` دریافت می‌شوند.
- endpoint active فقط `Offer.status=ACTIVE` را با ترتیب `created_at DESC` برمی‌گرداند.
- client آفر activeای را که `expires_at_ts` آن گذشته باشد از لیست active حذف می‌کند.
- برای کاربر غیرمشتری و غیرحسابدار، تاریخچه ۴۸ ساعت اخیر نیز از `GET /api/offers/market-history` دریافت می‌شود.
- صفحه اول history شامل ۲۵ ردیف است و history امکان load-more دارد.
- history شامل آفرهای معامله‌شده، منقضی/لغوشده قابل نمایش و stale-activeهای عبورکرده از زمان انقضا است.
- ترتیب history بر اساس زمان رخداد terminal و سپس زمان ساخت، هر دو نزولی است.
- UI ابتدا block آفرهای active و سپس block history را قرار می‌دهد؛ این دو block به‌صورت global دوباره sort نمی‌شوند.
- اگر یک شناسه همزمان در active و history وجود داشته باشد، نسخه history آن دوباره نمایش داده نمی‌شود.
- رخداد create باعث refresh feed active می‌شود.
- رخداد update وضعیت active را اصلاح می‌کند.
- رخداد expired/completed آفر را از active خارج و history را refresh می‌کند.
- کارت history read-only است و برچسب `منقضی` یا `معامله‌شده` دارد.

شواهد اصلی baseline:

- `frontend/src/views/MarketView.vue`
- `frontend/src/composables/useOffers.ts`
- `frontend/src/components/OffersList.vue`
- `api/routers/offers.py`
- `frontend/src/views/MarketView.test.ts`
- `frontend/src/composables/useOffers.test.ts`

### گزینه‌ها

#### گزینه A - فقط آفرهای active

در `رصد بازار` فقط آفرهای فعال نمایش داده شوند و history صرفاً داخل پروفایل کاربر قابل مشاهده باشد.

مزیت:

- ساده‌ترین و سبک‌ترین صفحه مدیریتی

ایراد:

- با نمای پیش‌فرض فعلی بازار یکسان نیست.
- آفر بلافاصله پس از معامله یا انقضا از context مدیر ناپدید می‌شود.
- مدیر برای هشدار درباره آفر تازه منقضی‌شده مجبور به جست‌وجوی مجدد می‌شود.

نتیجه پیشنهادی: `REJECT`

#### گزینه B - feed مرکب مشابه نمای پیش‌فرض بازار

`رصد بازار` همان active block و history block فعلی را بدون کنترل فیلتر نمایش دهد.

مزیت:

- با مدل ذهنی «عین آفرهای بازار» هم‌راستا است.
- context آفر پس از معامله یا انقضا باقی می‌ماند.
- هیچ feed یا ranking مدیریتی جداگانه ساخته نمی‌شود.

ایراد:

- باید identity به هر دو نوع کارت active و history اضافه شود.

نتیجه پیشنهادی: `ACCEPT`

#### گزینه C - feed مدیریتی مستقل با sort یا pagination متفاوت

مدیر همه آفرها را با ترتیب یا اندازه صفحه مستقل از بازار عمومی ببیند.

مزیت:

- آزادی بیشتر برای طراحی مدیریتی

ایراد:

- اصل parity را می‌شکند.
- ممکن است مدیر آفرهایی را ببیند که در پنجره قابل دسترس بازار عمومی نیستند.
- دوباره یک منبع رفتار جدا برای بازار ایجاد می‌کند.

نتیجه پیشنهادی: `REJECT`

### تصمیم پیشنهادی C01

`رصد بازار` آینه نمای پیش‌فرض بازار عمومی برای یک مدیر است، با یک تفاوت مجاز: context هویتی و اقدامات مدیریتی.

قرارداد دقیق پیشنهادی:

1. صفحه هیچ filter chip، search، sort selector یا فیلتر نقش/کاربر ندارد.
2. scope ثابت صفحه معادل `همه آفرها + همه تسویه‌ها` است.
3. feed از دو block تشکیل می‌شود:
   - ابتدا active offers
   - سپس terminal history قابل نمایش در ۴۸ ساعت اخیر
4. active block با `created_at DESC` مرتب می‌شود.
5. history block با `history_event_at DESC` و سپس `created_at DESC` مرتب می‌شود.
6. active و history با هم global sort نمی‌شوند؛ ترتیب blockها مانند بازار فعلی محفوظ می‌ماند.
7. terminal rowها read-only هستند، اما مدیر می‌تواند از همان row وارد context کاربر یا اقدام هشدار شود.
8. دکمه‌ها و interaction معامله در `رصد بازار` وجود ندارند؛ یکسانی مربوط به محتوا، ترتیب و وضعیت کارت است، نه امکان معامله.
9. قیمت، مقدار، مانده، نوع تسویه، کالا، لات‌ها، توضیح، timer و status stamp باید دقیقاً از همان public-card projection بازار استفاده کنند.
10. raw price یا فیلد تجاری اضافه فقط به دلیل admin بودن در کارت نمایش داده نمی‌شود.
11. نوار هویت و actionهای مدیریتی بعد از projection عمومی کارت اضافه می‌شوند و نباید مقادیر عمومی کارت را تغییر دهند.
12. مقایسه parity بر اساس ترتیب `offer_public_id`ها و محتوای عمومی کارت انجام می‌شود؛ identity band در مقایسه نادیده گرفته می‌شود.
13. قرارداد active feed به عدد ثابت یا محدودیت موقت فعلی گره نمی‌خورد و بر مبنای رفتار اصلاح‌شده بازار عمومی تعریف می‌شود.

### قرارداد دسترسی به feed

قرارداد `رصد بازار` به محدودیت‌ها یا خطاهای موقت پیاده‌سازی feed فعلی وابسته نمی‌شود.

قرارداد پیشنهادی:

- active feed در `رصد بازار` باید از قرارداد اصلاح‌شده و مشترک بازار عمومی پیروی کند.
- در Stage 0 هیچ سقف ثابت یا page size مستقلی برای active offerها تعیین نمی‌شود.
- اگر بازار عمومی از pagination، load-more یا infinite scroll استفاده کند، `رصد بازار` نیز همان سازوکار مشترک را مصرف می‌کند.
- مجموعه و ترتیب active offerهای قابل دسترس در snapshot یکسان باید در بازار عمومی و `رصد بازار` برابر باشد.
- پیاده‌سازی نباید برای سازگاری ظاهری، خطای فعلی active feed را در endpoint یا UI مدیریتی تکرار کند.
- قرارداد history فعلی، شامل صفحه اول ۲۵ ردیفی و load-more، تا زمان بررسی مستقل `AMM-C12` بدون تغییر باقی می‌ماند.

### قرارداد transition و Realtime

#### ایجاد آفر

- create event باعث refresh authoritative active feed می‌شود.
- آفر جدید بر اساس ترتیب backend در active block قرار می‌گیرد.
- event عمومی همچنان بدون هویت باقی می‌ماند؛ identity از read model مجاز admin تأمین می‌شود.

#### به‌روزرسانی مقدار یا قیمت

- row active بدون تغییر جایگاه غیرضروری patch/refresh می‌شود.
- محتوای عمومی کارت در بازار و `رصد بازار` باید برابر بماند.

#### معامله، انقضا یا لغو

- row از active block حذف می‌شود.
- history به‌صورت silent refresh می‌شود.
- در صورت قرارگرفتن در قرارداد history، همان `offer_public_id` در history block read-only ظاهر می‌شود.
- هیچ لحظه‌ای نباید یک آفر دوبار در feed ترکیبی نمایش داده شود.

#### خطای موقت شبکه یا sync lag

- داده موجود به‌دلیل خطای transient پاک نمی‌شود.
- refresh بعدی باید همگرایی را برقرار کند.
- صفحه نباید با payload Realtime عمومیِ بدون هویت، identity قبلی را null یا اشتباه کند.
- اگر parity میان public و admin feed در staging قابل اثبات نباشد، release متوقف می‌شود.

### سناریوهای منفی

- `رصد بازار` نباید فقط به‌خاطر admin بودن، آفر archived یا خارج از history window را نشان دهد.
- نباید آفر اولیه‌ای که هرگز به بازار منتشر نشده است در history مدیریتی بازار ظاهر شود.
- نباید آفر tier/customer-specific خارج از قرارداد بازار عمومی به feed اضافه شود.
- نباید به دلیل نبود identity، کل آفر از feed حذف شود؛ row عمومی باقی می‌ماند و identity حالت کنترل‌شده `نامشخص/حذف‌شده` می‌گیرد که قرارداد دقیق آن در `AMM-C02` بسته می‌شود.
- نباید فیلترهای مخفی URL یا query باعث تفاوت feed مدیران مختلف شوند.

### معیارهای پذیرش قابل تست

1. در snapshot یکسان، ترتیب `offer_public_id`های public default feed و admin feed برابر باشد.
2. active rows پیش از history rows قرار بگیرند.
3. active rows بر اساس `created_at DESC` باشند.
4. history rows بر اساس `history_event_at DESC, created_at DESC` باشند.
5. یک شناسه در feed ترکیبی تکرار نشود.
6. create event هر دو surface را به مجموعه یکسان همگرا کند.
7. completed/expired event آفر را از active به history منتقل کند.
8. terminal row در `رصد بازار` هیچ کنترل معامله‌ای نداشته باشد.
9. active row در `رصد بازار` نیز هیچ کنترل معامله‌ای نداشته باشد.
10. هیچ filter chip یا sort selector در صفحه وجود نداشته باشد.
11. داده عمومی کارت در دو صفحه برابر و فقط identity/action area اضافه باشد.
12. non-admin نتواند endpoint یا projection دارای identity را دریافت کند.
13. برابری مجموعه کامل active offerهای قابل دسترس در دو صفحه بدون وابستگی به یک عدد ثابت تست شود.
14. failure موقت refresh، آخرین feed سالم را پاک نکند.

### dependencyها

- `AMM-C03`: read model و Realtime بدون نشت identity

### stop conditionهای C01

- admin feed آفر اضافه یا کم نسبت به public default feed داشته باشد.
- ترتیب blockها یا rowها بین دو صفحه متفاوت شود.
- identity از event یا endpoint عمومی بازار قابل استخراج شود.
- terminal row امکان معامله داشته باشد.
- تغییر یک کارت عمومی در یک صفحه اعمال و در صفحه دیگر اعمال نشود.

## AMM-C02 - قرارداد هویت آفر‌دهنده و رابطه مشتری

### وضعیت

`DECIDED`

### پرسش

در `رصد بازار` هویت آفر‌دهنده چگونه نمایش داده شود و اگر آفر‌دهنده مشتری است، رابطه او با مالک حساب چگونه بیان شود بدون اینکه شخص دیگری به‌عنوان آفر‌دهنده معرفی شود؟

### تعریف واژه‌ها

- **آفر‌دهنده:** همان کاربری که آفر به نام او ثبت شده و تعهد بازار متعلق به اوست.
- **مالک رابطه مشتری:** کاربر اصلی‌ای که مشتری در ساختار مدیریتی به او متصل است؛ این شخص صاحب آفر مشتری نیست.
- **نام مدیریتی مشتری:** alias کمکی برای شناسایی مشتری در context مالک رابطه؛ این نام جای هویت اصلی مشتری را نمی‌گیرد.

### واقعیت فعلی پروژه

- کاربر عادی آفر را به نام خودش ثبت می‌کند.
- مشتری سطح ۱ آفر را به نام خودش ثبت می‌کند؛ بنابراین خود مشتری آفر‌دهنده است.
- مشتری سطح ۲ مجاز به ثبت آفر نیست.
- حسابدار به بازار و ثبت آفر دسترسی ندارد.
- مدل داده یک فیلد داخلی actor دارد، اما این فیلد یک سناریوی محصولی برای نمایش «ثبت‌کننده متفاوت» در `رصد بازار` ایجاد نمی‌کند.
- feed عمومی بازار هویت آفر‌دهنده یا رابطه مشتری را منتشر نمی‌کند.
- پس از حذف کاربر یا قطع رابطه مشتری ممکن است بخشی از context هویتی در دسترس نباشد، اما خود کارت آفر باید باقی بماند.

شواهد اصلی baseline:

- `models/offer.py`
- `core/services/offer_creation_service.py`
- `core/services/customer_relation_service.py`
- `api/routers/offers.py`
- `core/services/user_deletion_service.py`
- `tests/test_offers_router_create_success.py`
- `tests/test_offers_router_create_guards.py`

### گزینه‌ها

#### گزینه A - نمایش آفر‌دهنده واقعی با context مشتری

در هر کارت فقط صاحب واقعی آفر با label `آفر‌دهنده` نمایش داده شود. اگر این کاربر مشتری است، سطح مشتری و مالک رابطه در یک context جداگانه نشان داده شوند.

مزیت:

- با تمام مسیرهای مجاز فعلی بازار سازگار است.
- مدیر مستقیماً همان کاربری را می‌بیند که آفر به نام اوست.
- مالک رابطه مشتری با آفر‌دهنده اشتباه نمی‌شود.
- مفهوم فنی actor وارد UI محصول نمی‌شود.

نتیجه پیشنهادی: `ACCEPT`

#### گزینه B - نمایش مالک رابطه به‌جای مشتری

اگر آفر متعلق به مشتری باشد، مالک رابطه به‌عنوان آفر‌دهنده نمایش داده شود.

ایراد:

- شخص اشتباهی مسئول آفر معرفی می‌شود.
- تکرار قیمت اشتباه به حساب مالک رابطه نوشته می‌شود، نه مشتری واقعی.

نتیجه پیشنهادی: `REJECT`

#### گزینه C - نمایش actor داخلی به‌عنوان ثبت‌کننده دوم

در کنار آفر‌دهنده، actor داخلی نیز با یک هویت محصولی جدا نمایش داده شود.

ایراد:

- برای مسیرهای مجاز فعلی بازار سناریوی واقعی ندارد.
- حسابدار مجاز به ثبت آفر نیست.
- یک جزئیات فنی را به مفهوم محصولی گمراه‌کننده تبدیل می‌کند.

نتیجه پیشنهادی: `REJECT`

| مشتری سطح ۲ | آفر معتبر ندارد | ندارد | این حالت نباید از مسیر مجاز ایجاد شود |
| رابطه مشتری قطع یا ناموجود | خود مشتری | `رابطه در دسترس نیست` | هویت مشتری نمایش داده شود و context رابطه جعل نشود |
| کاربر حذف‌شده یا هویت ناموجود | `کاربر حذف‌شده/نامشخص` | در صورت دسترس context معتبر | کارت آفر باقی بماند و fallback کنترل‌شده نمایش داده شود |
| actor داخلی متفاوت | صاحب ثبت‌شده آفر | actor در UI نادیده گرفته می‌شود | فقط `آفر‌دهنده` نمایش داده شود |

### تصمیم پیشنهادی C02

1. در تمام کارت‌های `رصد بازار` فقط یک هویت اصلی با label دقیق `آفر‌دهنده` نمایش داده می‌شود.
2. آفر‌دهنده همان صاحب ثبت‌شده آفر است.
3. هیچ label یا هویت جداگانه‌ای با عنوان `ثبت‌کننده` در صفحه نمایش داده نمی‌شود.
4. actor داخلی وارد identity band، نمای سریع یا مسیر اقدام مدیریتی نمی‌شود.
5. در آفر مشتری، خود مشتری آفر‌دهنده است و مالک رابطه جایگزین او نمی‌شود.
6. برای مشتری سطح ۱، سطح مشتری و context جداگانه `مشتریِ: <مالک رابطه>` نمایش داده می‌شود.
7. نام مدیریتی مشتری می‌تواند alias کمکی باشد، اما هویت اصلی مشتری را حذف یا جایگزین نمی‌کند.
8. کلیک روی نام آفر‌دهنده، نمای سریع همان آفر‌دهنده را باز می‌کند.
9. مالک رابطه مشتری فقط از context رابطه و در محدوده مجوزهای مدیریتی قابل مشاهده است.
10. نبود هویت یا رابطه باعث حذف کارت آفر نمی‌شود؛ fallback صریح و غیرحدسی نمایش داده می‌شود.
11. C02 هیچ دسترسی تازه‌ای برای حسابدار یا مشتری سطح ۲ به بازار ایجاد نمی‌کند.
12. هویت آفر‌دهنده و context رابطه مشتری به feed، cache یا Realtime عمومی بازار اضافه نمی‌شود.

### رفتار نمای سریع

#### کاربر عادی

- کلیک روی نام آفر‌دهنده، نمای سریع همان کاربر را باز می‌کند.
- نقش یا هویت دوم برای آفر ساخته نمی‌شود.

#### مشتری سطح ۱

- نمای سریع، هویت خود مشتری را به‌عنوان آفر‌دهنده نشان می‌دهد.
- سطح مشتری، نام مدیریتی و مالک رابطه در بخش context مشتری قرار می‌گیرند.
- مالک رابطه به‌عنوان creator یا صاحب آفر معرفی نمی‌شود.

#### هویت یا رابطه ناموجود

- کارت آفر باقی می‌ماند.
- اگر هویت کاربر در دسترس نیست، label کنترل‌شده `کاربر حذف‌شده/نامشخص` نمایش داده می‌شود.
- اگر فقط رابطه مشتری در دسترس نیست، هویت آفر‌دهنده حفظ و فقط context رابطه ناموجود اعلام می‌شود.

### سناریوهای منفی

- مالک رابطه مشتری به‌جای خود مشتری آفر‌دهنده نمایش داده نشود.
- حسابدار یا actor داخلی در identity band ظاهر نشود.
- نام مدیریتی مشتری به‌تنهایی جای هویت اصلی مشتری را نگیرد.
- نبود رابطه مشتری باعث حذف یا تغییر آفر‌دهنده نشود.
- نبود هویت باعث حذف کل کارت آفر نشود.
- کلیک روی آفر‌دهنده، پروفایل مالک رابطه را باز نکند.
- non-admin هیچ داده هویتی مدیریتی را از API، cache یا event عمومی دریافت نکند.

### معیارهای پذیرش قابل تست

1. هر کارت حداکثر یک هویت اصلی با label `آفر‌دهنده` داشته باشد.

3. مشتری سطح ۱ خودش آفر‌دهنده و مالک رابطه فقط context تکمیلی باشد.

5. actor داخلی حتی در صورت تفاوت با صاحب آفر در UI نمایش داده نشود.
6. نام مدیریتی مشتری جای هویت اصلی مشتری را نگیرد.
7. نبود رابطه، آفر‌دهنده را تغییر ندهد و کارت را حذف نکند.
8. نبود هویت، fallback صریح و بدون حدس نشان دهد.
9. نمای سریع همیشه برای همان آفر‌دهنده باز شود.
10. public market response و Realtime عمومی فاقد تمام فیلدهای identity مدیریتی باشند.
11. identity band در active و terminal history قرارداد یکسان داشته باشد.
12. هویت آفر‌دهنده در هر دو سرور برای `offer_public_id` یکسان همگرا باشد.

## AMM-C03 - قرارداد جداسازی هویت از API و Realtime عمومی

### وضعیت

`DECIDED`

### پرسش

هویت آفر‌دهنده و context مشتری چگونه به صفحه `رصد بازار` برسد، بدون اینکه از پاسخ بازار عمومی، WebSocket، SSE، cache، Web Push، URL یا log برای کاربران دیگر قابل استخراج باشد؟

### واقعیت فعلی پروژه

- serializer آفر می‌تواند پاسخ دارای هویت یا بدون هویت بسازد.
- endpointهای عمومی active و history با حالت بدون هویت پاسخ می‌دهند.
- رخداد عمومی ایجاد آفر، `user_id` را null و نام کاربر را خالی منتشر می‌کند.
- مسیر sync نیز رخداد آفر foreign را با همین projection بدون هویت منتشر می‌کند.
- WebSocket فعلی پس از احراز هویت، همه کاربران را به channelهای عمومی یکسان متصل می‌کند و نقش مدیر را برای channel آفر تفکیک نمی‌کند.
- SSE نیز همان channelهای عمومی بازار را مصرف می‌کند.
- `publish_event` علاوه بر Redis، payload را مستقیماً برای تمام connectionهای فعال broadcast می‌کند.
- sanitization فعلی بر denylist چند فیلد حساس تکیه دارد و به‌تنهایی مانع قطعی انتشار اشتباهی هویت آفر‌دهنده نیست.
- frontend در رخداد create، feed را دوباره می‌خواند و در رخدادهای update/terminal نیز state را همگرا می‌کند.
- dependency مشترک `verify_admin_user` برای پذیرش مدیر میانی و مدیر ارشد وجود دارد.
- endpoint یا read model مستقل برای feed هویتی `رصد بازار` هنوز وجود ندارد.

### گزینه‌ها

#### گزینه A - پاسخ متفاوت از همان endpoint عمومی بر اساس نقش

همان URL بازار عمومی برای مدیر پاسخ دارای هویت و برای سایر کاربران پاسخ بدون هویت برگرداند.

مزیت:

- endpoint کمتری ساخته می‌شود.

ایراد:

- قرارداد یک URL بر اساس نقش تغییر می‌کند.
- احتمال اشتباه در cache، تست، proxy یا reuse frontend بالا می‌رود.
- یک flag یا خطای permission می‌تواند هویت را وارد surface عمومی کند.

نتیجه پیشنهادی: `REJECT`

#### گزینه B - API مستقل admin-only و Realtime عمومی بدون هویت

صفحه `رصد بازار` feed هویتی را فقط از API مدیریتی مستقل می‌خواند. رخدادهای عمومی هیچ هویتی ندارند و فقط صفحه را وادار به refresh همان API مدیریتی می‌کنند.

مزیت:

- مرز امنیتی قابل فهم و قابل تست است.
- public market و Realtime آن برای همه نقش‌ها دقیقاً یکسان باقی می‌ماند.
- نیاز به channel هویتی جدید و role-aware WebSocket از بین می‌رود.
- event گم‌شده با refresh کامل یا polling قابل جبران است.

نتیجه پیشنهادی: `ACCEPT`

#### گزینه C - channel Realtime جداگانه با payload هویتی

مدیران علاوه بر feed اولیه، updateهای دارای هویت را از channel اختصاصی دریافت کنند.

مزیت:

- تعداد refetchها کمتر می‌شود.

ایراد:

- اتصال WebSocket فعلی role-aware نیست و direct broadcast نیز عمومی است.
- لغو نقش، reconnect، Redis subscription و SSE باید همزمان مرز امنیتی تازه‌ای را enforce کنند.
- برای نسخه اول، هویت در event ارزش محصولی مستقلی نسبت به refetch ندارد.

نتیجه پیشنهادی: `REJECT_FOR_INITIAL_RELEASE`

### تصمیم پیشنهادی C03

1. `رصد بازار` یک read endpoint مستقل و admin-only دارد.
2. endpoint عمومی بازار هیچ query flag، header یا حالت اختیاری برای افزودن هویت دریافت نمی‌کند.
3. backend در هر درخواست read مدیریتی، نقش مدیر میانی یا مدیر ارشد را کنترل می‌کند؛ route guard frontend به‌تنهایی معتبر نیست.
4. read model مدیریتی همان feed مصوب C01 را با identity مصوب C02 ترکیب می‌کند.
5. پاسخ مدیریتی فقط هویت آفر‌دهنده و context مجاز مشتری را اضافه می‌کند؛ actor داخلی در آن وجود ندارد.
6. هیچ رخداد Realtime عمومی یا اختصاصی برای حمل هویت آفر‌دهنده ساخته نمی‌شود.
7. رویدادهای lifecycle آفر در WebSocket و SSE برای همه نقش‌ها، حتی مدیر، بدون هویت باقی می‌مانند.
8. صفحه `رصد بازار` با دریافت create/update/expired/completed یک silent refetch از API مدیریتی انجام می‌دهد.
9. reconnect و بازگشت visibility نیز باعث refetch کامل feed مدیریتی می‌شود.
10. projection رخداد عمومی آفر باید allowlist صریح داشته باشد؛ اتکا به denylist عمومی sanitization برای جلوگیری از نشت هویت کافی نیست.
11. مسیر Redis و direct broadcast باید دقیقاً یک payload عمومی و بدون هویت منتشر کنند.
12. پاسخ API مدیریتی با `Cache-Control: private, no-store` ارائه می‌شود و در service worker، cache عمومی، localStorage یا IndexedDB پایدار ذخیره نمی‌شود.
13. state هویتی فقط در حافظه session جاری WebApp نگه داشته می‌شود.
14. در logout، لغو session یا پاسخ 401/403، identity state بلافاصله پاک و صفحه مدیریتی بسته می‌شود.
15. خطای transient شبکه یا 5xx می‌تواند آخرین snapshot مجاز را با حالت stale نگه دارد، اما 401/403 هرگز به حفظ snapshot منجر نمی‌شود.
16. خطا، log، metric و URL نباید نام، شناسه داخلی کاربر یا context مشتری را ثبت کنند.
17. Web Push عمومی و پیام یا channel عمومی بازار از قرارداد هویت مدیریتی بی‌تأثیر می‌مانند.

### رفتار Realtime پیشنهادی

#### ایجاد آفر

- همه کاربران event بدون هویت را دریافت می‌کنند.
- بازار عمومی feed عمومی را refresh می‌کند.
- `رصد بازار` feed admin-only را refresh و identity را از read model می‌گیرد.

#### تغییر، معامله یا انقضا

- event فقط شناسه عمومی/فنی لازم و وضعیت عمومی تغییر را حمل می‌کند.
- صفحه مدیریتی هیچ identity موجود در event را مصرف نمی‌کند.
- پس از refresh، active/history و identity از snapshot واحد همگرا می‌شوند.

#### sync آفر foreign-home

- sync ابتدا داده را روی peer اعمال می‌کند.
- پس از apply، event عمومی بدون هویت منتشر می‌شود.
- refetch مدیریتی هویت را از داده محلی همگام‌شده می‌خواند.
- اگر identity هنوز نرسیده باشد، row آفر باقی می‌ماند و حالت کنترل‌شده `هویت در حال همگام‌سازی` نمایش داده می‌شود؛ هویت دیگری حدس زده نمی‌شود.

#### گم‌شدن event یا reconnect

- refetch کامل هنگام reconnect، visibility return یا polling همگرایی را بازیابی می‌کند.
- correctness به دریافت تک‌تک eventها وابسته نیست.

### قرارداد cache و پاک‌سازی state

- API مدیریتی در CDN یا reverse proxy به‌صورت shared cache ذخیره نمی‌شود.
- response هویتی در service worker یا storage پایدار مرورگر نوشته نمی‌شود.
- کلید cache عمومی بازار هرگز پاسخ admin را دریافت نمی‌کند.
- logout و role downgrade، state هویتی و نمای سریع باز را پاک می‌کنند.
- تغییر کاربر در همان browser نباید snapshot مدیر قبلی را به session جدید نشان دهد.

### سناریوهای منفی

- افزودن `?include_identity=true` به endpoint عمومی نباید هویت برگرداند.
- مدیر از WebSocket یا SSE عمومی payload هویتی دریافت نکند.
- non-admin با فراخوانی مستقیم URL مدیریتی پاسخ partial یا masked دریافت نکند؛ درخواست باید رد شود.
- payload هویتی قبل از permission check ساخته یا cache نشود.
- public event producer نتواند با اضافه‌کردن تصادفی `user_id` یا نام کاربر آن را broadcast کند.
- خطای serializer، stack trace یا log هویت را افشا نکند.
- پاسخ admin یک کاربر در browser session کاربر بعدی باقی نماند.
- در sync lag، relation یا آفر‌دهنده دیگری به‌عنوان fallback جایگزین نشود.

### معیارهای پذیرش قابل تست

1. پاسخ public market برای کاربر عادی، مدیر میانی و مدیر ارشد از نظر هویت یکسان و خالی باشد.
2. درخواست بدون session به API مدیریتی `401` بگیرد.
3. کاربر عادی، مشتری و حسابدار از API مدیریتی `403` بگیرند.
4. مدیر میانی و مدیر ارشد فقط فیلدهای هویتی مصوب C02 را دریافت کنند.
5. actor داخلی در response مدیریتی وجود نداشته باشد.
6. WebSocket عمومی برای تمام نقش‌ها از identity fields خالی باشد.
7. SSE عمومی برای تمام نقش‌ها از identity fields خالی باشد.
8. Redis publication و direct broadcast با allowlist یکسان تست شوند.
9. create محلی و create حاصل از sync هر دو event بدون هویت بسازند.
10. update، expired و completed نیز هیچ هویت اضافه نکنند.
11. رخداد Realtime باعث refetch API مدیریتی شود و identity از event patch نشود.
12. پاسخ مدیریتی headerهای `private, no-store` داشته باشد.
13. service worker و storage پایدار، response مدیریتی را نگه ندارند.
14. logout، session revoke و role downgrade فوراً identity state را پاک کنند.
15. 5xx آخرین snapshot مجاز را stale نگه دارد، اما 401/403 آن را پاک کند.
16. sync lag حالت `هویت در حال همگام‌سازی` بدهد و row را حذف یا با کاربر دیگر پر نکند.
17. تست منفی log و error response عدم وجود نام و شناسه داخلی کاربر را ثابت کند.

- امنیت event فقط به denylist عمومی متکی باشد.
- response هویتی در cache مشترک یا storage پایدار ذخیره شود.
- frontend پس از 401/403 یا تغییر session، identity قبلی را نگه دارد.
- identity از event patch شود و API مدیریتی منبع نهایی نباشد.
- direct broadcast و Redis path projection متفاوت داشته باشند.

## AMM-C04 - ماتریس مجوز مدیر میانی و مدیر ارشد

### وضعیت

`DECIDED`

### پرسش

مدیر میانی و مدیر ارشد کدام آفرها و اطلاعات را ببینند، روی کدام آفر‌دهنده‌ها چه اقدام‌هایی انجام دهند و مرز اختیار در سناریوهای self-target، اقدام روی مدیر دیگر و بازگرداندن تصمیم مدیر بالاتر چگونه باشد؟

### اصول تصمیم

1. مشاهده آفر از اجازه اقدام روی آفر‌دهنده جدا است.
2. مدیر میانی و مدیر ارشد همه آفرها و هویت واقعی آفر‌دهنده را بدون توجه به نقش او می‌بینند.
3. اطلاعات مرتبط با بازار، آفرهای اخیر و سابقه مدیریتی برای هر دو نقش قابل مشاهده است.
4. هدف مدیریتی دارای نقش `مدیر میانی` یا `مدیر ارشد`، برای مدیر میانی فقط‌خواندنی است.
5. کاربران `تماشا`، `عادی` و `پلیس` و کاربران دارای context مشتری یا حسابدار، هدف غیرمدیریتی محسوب می‌شوند.
6. اخراج محصولی همان غیرفعال‌سازی عضویت با حفظ داده و سابقه است، نه حذف دائمی.
7. تغییر نقش اقدام مستقیم `رصد بازار` نیست و فقط در مسیر مستقل مدیریت کاربران و با اختیار مدیر ارشد باقی می‌ماند.
8. همین قرارداد بدون تفاوت در WebApp و بات اجرا می‌شود.

### سناریوی مدیر میانی

1. مدیر میانی همه آفرها، از جمله آفر مدیران دیگر، را در جای صحیح feed می‌بیند.
2. برای target غیرمدیر، اقدام‌های انقضای همان آفر، هشدار، محدودیت و مسدودی و رفع آن‌ها در دسترس است.
3. اخراج و تغییر نقش در این surface در دسترس مدیر میانی نیست.
4. برای target مدیر، اطلاعات نمایش داده می‌شود اما actionها غیرفعال و علت `فقط مدیر ارشد مجاز است` روشن است.
5. مدیر میانی می‌تواند تصمیم مدیر میانی دیگری را روی target غیرمدیر با ثبت علت برگرداند.
6. مدیر میانی نمی‌تواند محدودیت، مسدودی یا تصمیم دیگری را که مدیر ارشد ثبت کرده برگرداند.

### سناریوی مدیر ارشد

1. مدیر ارشد روی هر target دیگری، از جمله مدیر میانی و مدیر ارشد دیگر، به اقدام‌های مدیریتی مصوب دسترسی دارد.
2. مدیر ارشد می‌تواند تصمیم هر مدیر میانی یا مدیر ارشد را با ثبت علت برگرداند.
3. مدیر ارشد می‌تواند عضویت target دیگری را غیرفعال کند.
4. غیرفعال‌سازی مدیر دیگر باید با تأیید صریح و نمایش واضح نقش و هویت target انجام شود.
5. حساب خود مدیر ارشد و آخرین مدیر ارشد فعال قابل غیرفعال‌سازی نیستند.

### رفتار UI مصوب

- برای اقدام مجاز، کنترل فعال و نتیجه آن در سابقه مشترک نمایش داده می‌شود.
- برای target مدیریتی در نمای مدیر میانی، اطلاعات حذف نمی‌شوند؛ action نامجاز غیرفعال و دلیل آن نمایش داده می‌شود.
- اگر target خود مدیر باشد، تمام actionهای مدیریتی غیرفعال و مسیر عادی بازار برای آفر شخصی یادآوری می‌شود.
- WebApp و بات باید برای یک actor و target یک مجموعه action یکسان نشان دهند.
- مخفی‌کردن دکمه در UI جایگزین کنترل قطعی مجوز هنگام اجرای اقدام نیست.

### تغییر نقش یا وضعیت هنگام مشاهده

- مجوز بر اساس نقش و وضعیت فعلی target در لحظه اقدام تعیین می‌شود، نه snapshot قدیمی صفحه.
- اگر نقش target بعد از نمایش تغییر کند، اقدام قدیمی بدون mutation رد می‌شود.
- WebApp یا بات snapshot را تازه و دلیل تغییر دسترسی را به مدیر اعلام می‌کند.
- اگر یک کاربر غیرمدیر به مدیر تبدیل شود، مدیر میانی فوراً فقط به مشاهده او محدود می‌شود.

### حفاظت‌های سلسله‌مراتب

- تصمیم مدیر ارشد توسط مدیر میانی قابل لغو نیست.
- تصمیم یک مدیر میانی توسط مدیر میانی دیگر فقط با علت و سابقه روشن قابل لغو است.
- اقدام مدیریتی self-target در `رصد بازار` برای هر دو نقش ممنوع است.
- آخرین مدیر ارشد فعال همیشه باید باقی بماند.
- غیرفعال‌سازی مدیر دیگر نیازمند تأیید صریح است و نباید با یک لمس ناخواسته اجرا شود.

### معیارهای پذیرش قابل تست

1. مدیر میانی و مدیر ارشد feed و هویت یکسانی دریافت کنند.
2. آفر target مدیر برای مدیر میانی مخفی نشود.
3. مدیر میانی برای target غیرمدیر بتواند آفر را منقضی و هشدار، محدودیت یا مسدودی اعمال کند.
4. مدیر میانی نتواند target غیرمدیر را اخراج یا نقش او را از `رصد بازار` تغییر دهد.
5. اقدام مدیر میانی روی target مدیر، حتی با درخواست مستقیم، بدون mutation رد شود.
6. مدیر میانی بتواند تصمیم مدیر میانی دیگر را با علت برگرداند.
7. مدیر میانی نتواند تصمیم مدیر ارشد را برگرداند.
8. مدیر ارشد بتواند روی مدیر دیگری اقدام کند و سابقه کامل ایجاد شود.
9. هیچ مدیر نتواند از `رصد بازار` روی خودش اقدام مدیریتی انجام دهد.
10. غیرفعال‌سازی آخرین مدیر ارشد فعال رد شود.
11. تغییر نقش target میان نمایش و اقدام، درخواست قدیمی را رد و snapshot را تازه کند.
12. مجموعه actionهای مجاز برای یک actor/target در بات و WebApp یکسان باشد.

## AMM-C05 - انقضای مدیریتی آفرهای Iran-home و foreign-home

### وضعیت

`DECIDED`

### پرسش

انقضای یک آفر مشخص از WebApp یا بات روی کدام سرور قطعی شود، مدیر چه زمانی نتیجه موفق ببیند و در حالت تکرار درخواست، رقابت با معامله، قطع ارتباط یا تأخیر side effect چه رفتاری الزامی باشد؟

### اصول تصمیم

1. انقضای مدیریتی فقط همان آفر انتخاب‌شده را هدف می‌گیرد.
2. علت انقضا الزامی و در confirmation همراه خلاصه آفر و هویت آفر‌دهنده نمایش داده می‌شود.
3. انقضا خودکار هشدار، محدودیت، مسدودی یا تغییر آفرهای دیگر کاربر ایجاد نمی‌کند.
4. فقط `offer_home_server` مجاز به قطعی‌کردن mutation است.
5. مبدأ اقدام، نقش مدیر، `user.home_server` یا محل session، مرجعیت آفر را تغییر نمی‌دهند.
6. موفقیت فقط پس از commit سرور مرجع اعلام می‌شود.
7. سرور غیرمرجع در حالت موفق، خطا یا outage نسخه محلی آفر را authoritatively تغییر نمی‌دهد.
8. مجوز مصوب `AMM-C04` بر اساس نقش فعلی مدیر و target در سرور مرجع دوباره بررسی می‌شود.
9. انقضای مدیریتی مشمول محدودیت تعداد یا نرخ self-expire آفر‌دهنده نیست.
10. اطلاع‌رسانی انقضا یک پیام خدماتی است و هشدار محصولی محسوب نمی‌شود.

### مسیر چهارگانه مصوب

| مبدأ اقدام | home server آفر | اجرای قطعی | رفتار سرور مبدأ |
| --- | --- | --- | --- |
| WebApp ایران | `iran` | ایران | انتظار برای commit محلی و سپس اعلام نتیجه |
| WebApp ایران | `foreign` | خارج | forward و انتظار برای پاسخ قطعی؛ بدون mutation محلی |
| بات خارج | `foreign` | خارج | انتظار برای commit محلی و سپس اعلام نتیجه |
| بات خارج | `iran` | ایران | forward و انتظار برای پاسخ قطعی؛ بدون mutation محلی |

تفاوت این چهار مسیر برای مدیر نمایش داده نمی‌شود و متن موفقیت، خطا و نتیجه نهایی محصولی در WebApp و بات یکسان است.

### جریان اقدام مدیر

1. action فقط برای آفر فعال و target مجاز در دسترس است.
2. مدیر با انتخاب action، خلاصه آفر، هویت آفر‌دهنده و فیلد علت را می‌بیند.
3. علت باید قبل از تأیید تکمیل شود و به آفر‌دهنده نیز نمایش داده خواهد شد.
4. پس از تأیید، کنترل تا روشن‌شدن outcome غیرفعال می‌شود تا double submit نسازد.
5. سرور مبدأ action را به home server صحیح می‌رساند.
6. home server مجوز و وضعیت جاری آفر را کنترل و فقط در حالت active بودن commit می‌کند.
7. پس از نتیجه قطعی، snapshot مدیریتی تازه و وضعیت نهایی به مدیر نشان داده می‌شود.

### نتیجه موفق و side effectها

پس از commit authoritative:

- وضعیت آفر `expired` و دلیل آن `admin_action` می‌شود.
- actor مدیر، علت، مبدأ WebApp یا بات، زمان و نتیجه در سابقه واحد ثبت می‌شوند.
- آفر از feed فعال home surface خارج می‌شود.
- تغییر نهایی برای peer sync می‌شود.
- ایران پس از apply محلی یا sync، WebApp و `رصد بازار` را refresh می‌کند.
- خارج وضعیت terminal پیام کانال Telegram را اعمال می‌کند.
- آفر‌دهنده در WebApp و پیام خصوصی بات، در هر سطحی که در دسترس باشد، پیام خدماتی حاوی علت دریافت می‌کند.

شکست sync، refresh، channel edit یا یکی از deliveryها بعد از commit، انقضا را rollback نمی‌کند. در این حالت مدیر می‌تواند نتیجه `آفر منقضی شد؛ به‌روزرسانی سایر بخش‌ها در حال انجام است` ببیند و side effect ناموفق باید retry/reconcile شود.

### مرز اطلاع‌رسانی و هشدار

- پیام انقضای مدیریتی فقط نتیجه اقدام را به آفر‌دهنده اعلام می‌کند.
- این پیام warning record نمی‌سازد و شمارنده یا سابقه هشدار کاربر را افزایش نمی‌دهد.
- اگر مدیر علاوه بر انقضا قصد هشدار داشته باشد، هشدار یک action مستقل مطابق `AMM-C06` است.
- retry انقضا نباید پیام خدماتی تکراری ایجاد کند.

### idempotency و تکرار

- هر تأیید مدیر یک action identity پایدار دارد.
- double click، refresh، retry شبکه و replay بین دو سرور با همان identity همان outcome را برمی‌گردانند.
- یک action موفق فقط یک mutation، یک سابقه و یک مجموعه notification منطقی می‌سازد.
- اگر پاسخ موفق گم شود، retry همان action metadata اقدام اول را بازمی‌گرداند و آن را بازنویسی نمی‌کند.
- retry نباید علت، actor یا زمان اقدام موفق اول را تغییر دهد.

### آفر terminal و رقابت

| وضعیت هنگام اجرا روی home server | نتیجه |
| --- | --- |
| آفر active است | انقضای مدیریتی commit می‌شود |
| همان action قبلاً موفق شده است | همان موفقیت قبلی بدون mutation یا سابقه جدید برمی‌گردد |
| مدیر دیگری زودتر آفر را منقضی کرده است | وضعیت `قبلاً منقضی شده` و outcome واقعی نمایش داده می‌شود؛ metadata قبلی حفظ می‌شود |
| مالک یا time limit زودتر آفر را منقضی کرده است | وضعیت نهایی واقعی نمایش داده و metadata قبلی حفظ می‌شود |
| معامله زودتر commit شده است | انقضا انجام نمی‌شود و وضعیت `معامله‌شده` نمایش داده می‌شود |
| انقضای مدیریتی زودتر commit شده است | درخواست معامله بعدی به‌دلیل غیرفعال‌بودن آفر رد می‌شود |

دو مدیر یا معامله و انقضا نباید هر دو به‌عنوان mutation موفق روی یک نسخه active ثبت شوند. فقط نخستین commit معتبر برنده است.

### قرارداد outage و timeout

#### سرور مرجع پیش از پذیرش در دسترس نیست

- هیچ mutation محلی انجام نمی‌شود.
- action برای اجرای خودکار پس از reconnect صف نمی‌شود.
- مدیر پیام عدم دسترسی موقت می‌بیند و پس از برقراری ارتباط باید آگاهانه دوباره اقدام کند.
- reconnect به‌تنهایی مجوز اجرای یک انقضای قدیمی نیست.

#### ممکن است commit انجام شده باشد اما پاسخ نرسیده است

- نتیجه شکست قطعی نمایش داده نمی‌شود.
- action در وضعیت `در حال بررسی نتیجه` باقی می‌ماند.
- سیستم با همان action identity، outcome واقعی home server را بازیابی می‌کند.
- تا تعیین تکلیف، action تازه برای همان intent ساخته نمی‌شود.
- اگر commit تأیید شود موفقیت قبلی نمایش داده می‌شود؛ اگر عدم پذیرش قطعی شود مدیر می‌تواند اقدام تازه‌ای آغاز کند.

### شناسه و خطای تطبیق آفر

- شناسه پایدار مشترک آفر مرجع cross-server action است و integer id محلی نباید مبنای فرض برابری دو سرور باشد.
- اگر home server آفر با شناسه پایدار را پیدا نکند، آفر دیگری حدس زده یا mutate نمی‌شود.
- mismatch هویت، مالک یا home server بدون mutation رد و snapshot مبدأ تازه می‌شود.
- forwarding اشتباه نباید loop یا hop نامحدود میان دو سرور ایجاد کند.

### معیارهای پذیرش قابل تست

1. WebApp آفر Iran-home را در ایران منقضی کند.
2. WebApp آفر foreign-home را فقط پس از commit خارج موفق نشان دهد و ایران محلی mutate نکند.
3. بات آفر foreign-home را در خارج منقضی کند.
4. بات آفر Iran-home را فقط پس از commit ایران موفق نشان دهد و خارج محلی mutate نکند.
5. مجوز C04 و self-target روی home server دوباره کنترل شوند.
6. علت خالی پذیرفته نشود و علت ثبت‌شده به آفر‌دهنده نمایش داده شود.
7. admin expiry تحت محدودیت self-expire مالک قرار نگیرد.
8. تکرار همان action فقط یک mutation، سابقه و notification منطقی بسازد.
9. دو مدیر همزمان فقط یک expiry موفق بسازند و metadata برنده حفظ شود.
10. race معامله و انقضا فقط یک وضعیت نهایی معتبر بسازد.
11. remote outage هیچ mutation محلی یا queued late-expiry نسازد.
12. timeout مبهم تا کشف outcome در حالت `در حال بررسی نتیجه` باقی بماند.
13. failure کانال، sync یا notification پس از commit، انقضا را rollback نکند.
14. پیام خدماتی انقضا warning record یا شمارنده هشدار نسازد.
15. mismatch شناسه پایدار بدون حدس آفر جایگزین و بدون mutation رد شود.

## AMM-C17 - قرارداد UI بات و refresh رصد بازار

### وضعیت

`DECIDED`

### پرسش

`رصد بازار` در بات چگونه نمایش داده شود، مدیر تا چه حد تغییرات را بدون refresh دستی ببیند و refreshهای مدیریتی چگونه بدون آسیب‌زدن به ظرفیت ارسال کانال اجرا شوند؟

### تصمیم ثبت‌شده

1. surface بات فقط در گفت‌وگوی خصوصی مدیر نمایش داده می‌شود.
2. dashboard از یک پیام قابل‌ویرایش استفاده می‌کند و برای هر navigation یا event پیام تازه نمی‌سازد.
3. آفرها صفحه‌بندی می‌شوند و دکمه‌های قبلی، بعدی و `به‌روزرسانی` همیشه در دسترس‌اند.
4. انتخاب هر آفر همان پیام را به نمای جزئیات و اقدام تبدیل می‌کند.
5. ورود به dashboard یک بازه مشاهده فعال می‌سازد و هر interaction آن را تمدید می‌کند.
6. در بازه مشاهده فعال، رخدادهای بازار تجمیع و همان پیام با هدف تأخیر ۵ تا ۱۰ ثانیه ویرایش می‌شود.
7. burst رخدادها به یک snapshot نهایی تبدیل می‌شود؛ یک edit برای هر event ممنوع است.
8. پس از پایان بازه مشاهده فعال، refresh خودکار متوقف و دکمه refresh دستی باقی می‌ماند.
9. هر callback مدیر snapshot را تازه می‌کند و باید سریع با `answerCallbackQuery` پاسخ داده شود.
10. dashboard هیچ پیام یا editای در chat کانال عمومی ایجاد نمی‌کند.
11. صف ارسال حیاتی کانال بر refresh dashboard اولویت دارد.
12. refresh مدیریتی کم‌اولویت، تجمیع‌پذیر و قابل جایگزینی است و برای هر dashboard فقط یک کار pending نگه می‌دارد.
13. خطای 429 طبق `retry_after` مدیریت می‌شود و retry سریع یا بی‌نهایت مجاز نیست.
14. paid broadcast برای refresh dashboard استفاده نمی‌شود.

### تفسیر Realtime در بات

- Realtime بات به معنی push یک پیام تازه برای هر تغییر نیست.
- مدیری که در بازه مشاهده فعال است، تغییرات تجمیع‌شده را معمولاً بدون refresh دستی و با چند ثانیه تأخیر می‌بیند.
- دکمه refresh مسیر قطعی بازیابی snapshot در تمام زمان‌ها است.
- Telegram حضور واقعی مدیر روی همان صفحه را گزارش نمی‌کند؛ بازه مشاهده فعال از آخرین interaction مدیر استنباط می‌شود.

### قرارداد محدودیت Telegram

- محدودیت per-chat کانال و چت خصوصی مدیر به‌دلیل chat مقصد متفاوت، مستقیماً یکی نیستند.
- ظرفیت کلی bot token و صف outbound مشترک است؛ بنابراین refresh زیاد مدیران می‌تواند غیرمستقیم روی ارسال کانال اثر بگذارد.
- ویرایش همان پیام از ایجاد سیل پیام جلوگیری می‌کند؛ Telegram سهمیه جدا و تضمین‌شده‌ای برای edit اعلام نکرده است، بنابراین دریافت 429 برای آن باید پیش‌بینی و مدیریت شود.
- اعداد rate limit نباید در منطق correctness هاردکد شوند؛ scheduler باید `retry_after` را رعایت کند.
