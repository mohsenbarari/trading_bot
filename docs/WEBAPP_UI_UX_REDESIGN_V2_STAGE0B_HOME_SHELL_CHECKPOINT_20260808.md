# Stage 0B-2 — خانه و پوسته احراز‌شده

تاریخ: ۲۰۲۶-۰۸-۰۸

وضعیت: تکمیل و تأیید مالک محصول در ۲۰۲۶-۰۸-۰۸ برای ادامه به `0B-3`؛ همه قاب‌های موبایل، قرارداد shell، width sweep و proof دسکتاپ در Figma رسمی ثبت و اعتبارسنجی شده‌اند؛ design-only و بدون مجوز تغییر کد محصول

شاخه: `condidate/webapp-ui-ux-redesign-v2`

جهت مصوب: **مالی مدرن**

## ۱. تصمیم مالک محصول و دامنه این checkpoint

مالک محصول ادامه مسیر از `0B-1` به `0B-2` را مجاز کرد و اعلام کرد که تأیید چهار دستیار خارجی فعلاً شرط پیشروی نیست. این تصمیم:

- گزارش‌های قبلی را به‌صورت صوری «تأییدشده» نمی‌کند؛
- یافته‌های معتبر و carry-forwardهای ثبت‌شده را حذف نمی‌کند؛
- پروتکل بازبینی خارجی را برای استفاده احتمالی آینده نگه می‌دارد؛
- گیت تصمیم خود مالک محصول و ممنوعیت شروع runtime تا پایان `0B-6` را تغییر نمی‌دهد.

مالک محصول سپس در ۲۰۲۶-۰۸-۰۸ خروجی این checkpoint و ادامه به `0B-3` را به‌صورت صریح تأیید کرد؛ این تأیید مجوز تغییر runtime نبود.

این checkpoint فقط قرارداد تجربه و شواهد طراحی **خانه و پوسته احراز‌شده** را می‌سازد. هیچ فایل runtime، endpoint، permission، صفحه داخلی بازار یا صفحه داخلی پیام‌رسان در دامنه تغییر نیست.

## ۲. هدف سناریویی

کاربر باید در چند ثانیه بفهمد:

1. اکنون در کدام حساب است؛
2. آیا موضوعی واقعاً نیازمند توجه اوست؛
3. اقدام بعدی قابل انجام چیست؛
4. آیا داده تازه، ذخیره‌شده، در حال اتصال مجدد یا ناموجود است.

حالت عادی عمداً خلوت می‌ماند. سلامت عادی حساب، تعداد معاملات، تعداد اعلان‌ها، همکاران، کالاها، aliasها، نقش و مسیرهای مجاز فقط برای پرکردن صفحه نمایش داده نمی‌شوند.

## ۳. non-goal و مرز محافظت‌شده

- فقط جایگاه کنترل/ویجت فعلی بازار در خانه رزرو می‌شود. داخل آن باید در artifact طراحی یک placeholder غیرهنجاری باشد و در پیاده‌سازی، widget فعلی بدون تغییر کپی/حفظ شود. نام‌گذاری node به‌تنهایی حفاظت محسوب نمی‌شود.
- مقصدهای «بازار» و «پیام‌رسان» در navigation حفظ می‌شوند؛ صفحه، FAB و رفتار داخلی آن‌ها بررسی یا بازطراحی نشده است.
- تاریخچه معاملات امروز، فهرست همکاران، کالاهای مجاز و اتصال تلگرام از نمای پیش‌فرض خانه خارج‌اند و به مقصد canonical یا نمایش on-demand منتقل می‌شوند.
- این checkpoint اجرای واقعی offline cache، PWA install، router guard، focus management یا session approval را اثبات نمی‌کند.

## ۵. قرارداد header و navigation

### Header

- فقط نام حساب جاری، avatar کوتاه، عنوان صفحه و یک کنترل اعلان؛
- بدون subtitle تکراری «حساب جاری»، greeting، role chip، خروج، «حساب فعال»، توضیح دسترسی یا مجموعه badgeها؛
- unread فقط یک خانه بصری دارد و dot و count هم‌معنا هم‌زمان نمایش داده نمی‌شوند.

### Bottom navigation

- ترتیب مقصدها حفظ می‌شود: خانه، بازار، پیام‌رسان، عملیات و حساب؛
- برای حسابدار، بازار واقعاً حذف و چهار مقصد با عرض برابر نمایش داده می‌شوند؛
- برای حساب غیرفعال، مقصد بازار از navigation حذف می‌شود تا dead destination ساخته نشود؛ این تصمیم درباره shell navigation است و مجوز تغییر widget بازار نیست؛
- active state با سطح کم‌رنگ و رنگ مشخص می‌شود، نه فقط تغییر رنگ icon؛
- icon و label هم‌زمان دیده می‌شوند و target تعاملی حداقل ۴۴×۴۴ است؛
- برچسب navigation در شواهد مرجع کمتر از ۱۱px نیست و در عرض ۳۶۰ نیز خوانا و بدون شکست است؛
- FAB و navigation اختصاصی داخل بازار/پیام‌رسان baseline محافظت‌شده باقی می‌مانند.

## ۷. قرارداد connection، error و PWA

- `loading` هویت یا سلامت حساب را حدس نمی‌زند.
- `offline` فقط می‌گوید داده ذخیره‌شده است؛ تا زمانی که retry معنی ندارد، دکمه بی‌اثر ساخته نمی‌شود.
- `stale/reconnecting` داده قبلی را حفظ می‌کند و به skeleton بازنمی‌گردد.
- زمان آخرین به‌روزرسانی فقط وقتی نمایش داده می‌شود که تصمیم کاربر را تغییر دهد.
- خطای قابل بازیابی، retry را کنار همان خطا قرار می‌دهد.
- recovery موفق با toast کوتاه و گذرا اعلام می‌شود، نه کارت موفقیت دائمی.
- PWA فقط پس از بارگذاری موفق خانه، در نبود هشدار فوری و به‌صورت inline و قابل رد نمایش داده می‌شود.
- PWA در login، loading، offline یا پشت modal امنیتی نمایش داده نمی‌شود.

اولویت لایه‌ها:

1. تأیید نشست/امنیت؛
2. connection و offline؛
3. toast نتیجه اقدام؛
4. پیشنهاد PWA؛
5. bottom navigation.

## ۹. معیار پذیرش

- آزمون پنج‌ثانیه‌ای هدف صفحه، هویت لازم و اقدام بعدی را روشن کند.
- حالت آرام صفر KPI، صفر شمارنده بی‌اقدام و صفر کارت تزئینی داشته باشد.
- صددرصد واحدهای همیشه‌نمایان در inventory توجیه داشته باشند.
- یک واقعیت در یک viewport فقط یک خانه بصری اصلی داشته باشد.
- loading، quiet، error، offline و stale با هم اشتباه نشوند.
- retry کنار خطای قابل‌بازیابی باشد.
- navigation فقط در shell واجد آن فضا رزرو کند و safe area را بپوشاند.
- قاب مرجع موبایل ۳۹۰×۸۴۴ و width sweep شامل ۳۶۰، ۳۷۵، ۳۹۰، ۴۱۴ و ۴۳۰ باشد.
- target عمومی حداقل ۴۴×۴۴ و CTA حداقل ۴۸ پیکسل ارتفاع داشته باشد.
- کنتراست متن عادی حداقل ۴٫۵:۱ و focus/state غیرمتنی حداقل ۳:۱ باشد.
- proof دسکتاپ اطلاعات تازه‌ای فقط برای پرکردن فضا اضافه نکند و navigation architecture تازه نسازد.
- artifact محصول هیچ ظاهر، status label یا CTA تازه‌ای برای widget محافظت‌شده بازار تجویز نکند.
- هدر subtitle تکراری «حساب جاری» نداشته باشد.
- هیچ کد runtime و هیچ فایل Market/Messenger تغییر نکند.

گیت فنی این checkpoint بسته است: Figma رسمی، screenshots مستقیم، responsive sweep، desktop proof، ممیزی ضرورت محتوا و harness مشتق‌شده همگی هم‌راستا و پاس هستند. مالک محصول در ۲۰۲۶-۰۸-۰۸ عبور به `0B-3` را به‌صورت صریح تأیید کرد؛ runtime همچنان تا تأیید صریح `0B-6` ممنوع است.

## ۱۰. carry-forwardهای پیاده‌سازی

- شکست `/api/auth/me` اکنون می‌تواند خانه را خالی بگذارد؛ Stage 1 باید error/retry واقعی بسازد.
- retry شبکه فعلی offline، stale و reconnecting را از هم جدا نمی‌کند؛ Stage 1 باید state machine روشن داشته باشد.
- shell فعلی روی همه routeها به‌جز login ظاهر می‌شود؛ Stage 3 باید public/focused/standard shell را جدا کند.
- prompt فعلی PWA global و overlay است؛ Stage 3 باید آن را به قرارداد inline پس از خانه سالم منتقل کند.
- مقصد بازار برای حساب غیرفعال و مقصد عملیات برای نقش فاقد اقدام باید در Stage 3/4 با permission واقعی هماهنگ شوند.
- فهرست معاملات امروز، همکاران، کالاها و اتصال تلگرام باید در Stage 4 به مقصد canonical یا on-demand منتقل شوند.
