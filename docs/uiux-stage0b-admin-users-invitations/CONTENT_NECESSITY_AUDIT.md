وضعیت: قرارداد محتوایی Phase 0 در بسته نهایی Figma با audit schema 7، در evidence محلی با `25 / 25` assertion و در بسته source-bound پیش‌نمایش خصوصی Sites پاس است؛ تأیید بصری مالک pending است.

## ممیزی state atlas

| state | Keep | Remove |
| --- | --- | --- |
| Loading | skeleton ساختاری و shell پایدار | هویت، تعداد، permission و status فرضی |
| Load error | پیام cause-neutral و retry نزدیک | empty دروغین، blame قطعی شبکه و جزئیات backend |
| True empty | تفاوت روشن نبود کاربر/دعوت و اقدام مجاز | عدد صفر، کارت آماری یا CTA ناممکن |
| Search empty | query فعلی و پاک‌کردن جست‌وجو | پیام true-empty یا پیشنهاد دعوت نامرتبط |
| Missing/deleted | توضیح حذف/عدم دسترسی و بازگشت معتبر | spinner نامحدود، ID و route فنی |
| Permission/self protected | علت کوتاه اثرگذار و action امن | افشای سیاست داخلی یا کنترل مخرب فعال |
| Busy/success/failure | feedback کنار action مبدأ | toast مبهم و پاک‌شدن زودهنگام context |
| Clipboard failure | retry copy یا بازکردن مستقیم مقصد موجود | success دروغین یا URL خام |
| Invitation stale | وضعیت تازه و recovery | revoke موفق دروغین |

## تصمیم‌های سراسری

### Keep

- هویت لازم برای جلوگیری از اقدام روی فرد اشتباه؛
- نقش/سطح و سرگروه فقط چون اختیار و تصمیم مدیریتی را تغییر می‌دهند؛
- وضعیت و محدودیت فعال وقتی action بعدی را تغییر می‌دهد؛
- deadline، مصرف سهمیه و پیامد قابل‌اجرا؛
- جست‌وجوی پایدار؛
- نشان غیرعددی «نیازمند رسیدگی» برای pending بارگذاری‌شده؛ صف می‌تواند آیتم‌های loaded را بدون total نمایش دهد؛
- feedback همان‌جا؛
- پیامد کامل اقدام امنیتی یا غیرفعال‌سازی.

### On demand

- نقش و کنترل‌های پیشرفته؛
- نشست‌ها و پایان همه نشست‌ها؛
- ظرفیت‌ها و محدودیت ارتباط؛
- اقدام حذف حساب با ارجاع به flow canonical قبلی.

### Remove

- تعداد کل کاربر، نقش، دسته، مسیر و ابزار؛
- total عددی pending از `array.length` endpoint محدود به ۱۰۰ و بدون total؛
- role chip و summary دسترسی؛
- فیلترهای role/status که روی مجموعه ناقص client-side اعمال می‌شوند؛
- علت، تاریخچه و audit محدودیت/دعوت که API یا surface فعلی پشتیبانی نمی‌کند؛ این‌ها فقط carry-forward خارج از دامنه‌اند؛
- route، API، backend، server و authority metadata؛
- هشدار مستقل خیالی؛
- گزینه محدودیت تعدادی دائمی تا حل قرارداد cross-platform؛
- نقش دعوت `super` و هر role خارج از matrix دقیق ادمین جاری؛
- ادعای تحویل Telegram بدون receipt؛
- URL خام در همه stateها، از جمله clipboard failure؛
- تکرار نام، status، deadline، URL یا پیامد در یک viewport؛
- card، badge، divider، icon یا helper صرفاً برای پرکردن فضای خالی.

## دسکتاپ و responsive

فضای دسکتاپ فقط برای هم‌زمان‌کردن فهرست و جزئیات همان کار استفاده می‌شود. KPI، نمودار، sidebar تازه، summary انتخاب تکراری یا metadata اضافی مجاز نیست. پنج عرض موبایل فقط fit و hierarchy همان محتوای ضروری را می‌سنجند و اطلاعات تازه‌ای به عرض بزرگ‌تر اضافه نمی‌کنند.

## قفل permission و نتیجه قابل ادعا

- هدف شخصی برای هر ادمین فقط قابل مشاهده است؛ تغییر نقش، محدودیت معامله، محدودیت تعدادی، غیرفعال‌سازی، پایان نشست‌ها و حذف همگی read-only هستند.
- مدیر ارشد هم‌سطح دیگر قابل مشاهده اما برای همان actionها، از جمله role edit، read-only است.
- مدیر ارشد فقط سطوح پایین‌تر را مدیریت می‌کند؛ مدیر میانی هیچ **ادمین دیگری** را target نمی‌گیرد و حساب خودش فقط استثنای visible/read-only است.
- permission atlas شش ردیف مستقل دارد؛ self مدیر میانی در ردیف visible/read-only از «هر مدیر دیگر» hidden جدا است.
- این قرارداد طراحی و carry-forward backend است، نه توصیف enforcement فعلی.
- success غیرفعال‌سازی فقط update قابل مشاهده account state/deadline را می‌گوید؛ confirm فقط خروج مورد انتظار کاربر از کانال را با نتیجه صریحاً تأییدنشده توضیح می‌دهد و ثبت/آغاز درخواست، حذف واقعی یا notification delivery Telegram بدون receipt ادعا نمی‌شود.
- غیرفعال‌سازی آفر را expire/collect نمی‌کند؛ این cascade فقط در حذف حساب دیده می‌شود.
- count authoritative و pagination واقعی صف pending carry-forward پیاده‌سازی‌اند.
- مدیر میانی فقط pendingهای ساخته‌شده توسط خودش و مدیر ارشد همه pendingها را می‌بیند/revoke می‌کند.
- همه مثال‌های نام، هویت و شماره تلفن در Figma، Sites و evidence محلی synthetic هستند.

## گیت نهایی

این inventory قرارداد ورودی طراحی است. تطبیق rootهای Figma، screenshotهای مستقیم، harness محلی و archive/source پیش‌نمایش خصوصی Sites با این جدول پاس شده و شواهد فنی Stage بسته است. محتوای signed-in live بدون bypass token واکشی نشده؛ بنابراین تأیید بصری مالک در URL owner-only هنوز لازم است و هیچ ادعای render ناشناس یا رفتار runtime وجود ندارد.
