# Release CI and Control Plane

- 2026-09-03 | `DPL-8` approved: one cross-site runtime image uses hash-locked dependencies and digest-pinned bases; CI emits SBOM, provenance, vulnerability evidence, manifest and signature. Integrity/secret failures and newly introduced reachable Critical vulnerabilities hard-block; old unchanged findings do not block an unrelated hotfix and instead receive an owned deadline. Scanner outages may reuse same-content evidence for up to 24h; exceptions are CVE/package/release-specific and expiring, never global.

- 2026-09-03 | Production installs no dependencies from the network. Iran caches Active/Previous/Candidate for offline deploy; Ansible checks OS patches without automatic install/reboot, targeting reachable Critical within 24h, High within 7d, and routine monthly windows. Dependency PRs are weekly without auto-merge. Keep other successful releases 30d, failed/partial builds 24h, SBOM/security summaries 180d, open-incident evidence until closure, and clean unreferenced cache weekly.

- 2026-09-03 | `DPL-7` approved: GitHub Actions becomes the primary CI and uses ephemeral hosted runners to test, build, sign and publish one immutable `READY` release; CI never auto-deploys. Either independent per-host Operations Dashboard may activate only `READY` releases, while local controllers journal, stage, smoke, commit or rollback and distinguish stale peers from failures. Ansible only provisions infrastructure; Finland has a constrained audited emergency builder only when GitHub CI is unavailable, never a general self-hosted runner.

- 2026-09-03 | Each dashboard uses username/password/TOTP without an IP allowlist and a 24-hour session; only Writer, DNS, R3 and force actions require fresh TOTP. Missing local journal/health/rollback blocks activation, but Grafana or notification-channel failure does not block a hotfix. Metrics, logs, deployment evidence and security audits use the approved bounded time-and-size retention policy.
