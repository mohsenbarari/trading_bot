# Physical WAL remote-ACK receiver ledger contract

`core.physical_wal_remote_ack_receiver_ledger` is a local, default-disabled,
root-only receipt ledger. It does not implement Object Storage, a network
endpoint, a PostgreSQL command, database recovery, Witness access, promotion,
writer admission, routing, shell execution, SSH, Docker, or encryption.

Its only state-changing operation is local: after all inputs are accepted, it
creates a canonical Ed25519 receipt and commits it to a protected filesystem
ledger before returning its bytes. The returned receipt remains signed
evidence; it is not a native PostgreSQL `remote_apply` result, a commit permit,
a Writer permit, a promotion permit, or proof that the entire deployment is
ready.

## Required inputs

The runtime accepts no raw source request. It requires an opaque
`VerifiedPhysicalWalRemoteAckRequest` produced by
`verify_physical_wal_remote_ack_request`; at issue time it rechecks the
capability, freshness, exact route/binding, and pinned source public key.

For a *new* receipt, it separately requires an opaque
`VerifiedPhysicalWalRemoteAckReceiverRecoveryEvidence`. The evidence verifier
does not open PostgreSQL: it validates a typed observation supplied by a future
trusted local receiver adapter. The observation must bind all of the following
to the exact canonical source-request SHA-256:

- source, receiver/destination, and deterministic request-binding hash;
- complete sorted manifest-hash and immutable `(object_key, version_id)` sets;
- a standby-in-recovery assertion and a replay LSN at or beyond the requested
  acknowledgement LSN; and
- a fresh receiver-evidence correlation hash and observation timestamp.

The evidence is intentionally separate from receipt signing. Directly
constructing either a source request or a recovery-observation dataclass does
not meet the runtime boundary: the opaque verifier capability is required.
The future PostgreSQL adapter must establish the underlying replay observation;
this module makes no claim that it did.

## Durable local semantics

The configured state root must already be an absolute, non-symlink,
root-owned `0700` directory, and the process must run as root. A fixed
root-owned child directory contains a `0600` lock and a canonical `0600`
ledger. The operation takes an exclusive `flock`, validates the complete
existing signed history, writes a new temporary `0600` file with `fsync`, uses
atomic `rename`, and then `fsync`s the containing directory. It refuses
symlinks, unexpected owners/modes, link counts, noncanonical JSON, a changed
route/key configuration, malformed history, and bounded-size violations.

Each durable entry retains enough non-secret material for later source-side
admission/audit of the exact pair:

- canonical source-request and destination-receipt bytes plus their SHA-256s;
- request and receipt IDs/nonces;
- exact request-binding hash and receipt acknowledgement time; and
- the verified recovery-evidence correlation hash, observed timestamp, and
  replay LSN.

Before reading an entry back, the ledger re-verifies both Ed25519 signatures
and the full configured route/binding at the receipt acknowledgement time.

## Replay and idempotency

A request ID is a durable identity, not a hint. If a retry presents the same
request ID and byte-identical request SHA-256, nonce, and binding, the ledger
returns the original byte-for-byte receipt without requiring either a fresh
recovery observation or the destination private key again. It never makes a
second receipt. The source request itself must still pass its normal protocol
freshness/capability check.

Any conflicting reuse fails closed: a changed request for an existing request
ID, a request nonce reused under another request ID, a collision between a
request identity and receipt identity, or malformed/tampered persisted history
all block issuance. New receipt IDs/nonces are generated by the local runtime,
not chosen by the source request.

The ledger is finite (default 256 entries) and refuses a new receipt when its
configured bound is reached. Retention/compaction is deliberately not
implemented here because it needs a separately reviewed source-admission and
audit-retention protocol.

## Remaining boundary

This closes only the local durable receipt/replay-idempotency gap. A real
implementation still needs an independently trusted PostgreSQL recovery
adapter, continuous Object-Storage pull/replay cursor, source-side database
write admission tied to the stored receipt, live Witness CAS/term checks,
former-writer fencing, and the destructive Full Matrix execution harness.
